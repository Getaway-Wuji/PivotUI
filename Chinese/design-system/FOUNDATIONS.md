# 界面共用设计规范

版本：0.2  
建立日期：2026-11-14  
状态：共用规则已建立，视觉风格等待用户提供参考样式。

本规范供界面设计系列 skills 共同使用，约定同一产品各页面应保持一致的设计方法、组件行为和协作方式。后续每个区块依据用户提供的参考样式形成自己的专业设计方法，并继承该产品已确定的全局视觉设定。自制与外源模块的分工见 [Skills 联动方案](ORCHESTRATION.md)。

## 1 适用范围与执行原则

适用于后台页面框架、Dashboard 仪表盘、数据列表、表单、详情页、设置页面，以及官网、作品集和旧站改版中相关的共用设计工作。业务数据规则用于业务区域，营销叙事规则用于展示区域；各模块的细节在对应 skill 和模块记录中补充。

- 围绕页面使用者的工作组织内容：他要看懂什么、判断什么、执行什么操作。
- 视觉层级服务于信息重要性。优先通过位置、尺寸、字重、间距和分组表达层级，再决定颜色和装饰的使用。
- 同一产品中相同语义、相同组件、相同交互使用一致的表达。确有差异时记录适用场景。
- 信息密度由工作场景和参考样式决定；紧凑、高留白、明暗主题均可成为有效方向。
- 已有项目优先复用其组件、样式变量和交互习惯。用户指定重设计时，在本次范围内更新。
- 用户明确要求优先；出现冲突时先判断影响范围。能在模块内部解决的差异直接处理，影响多个页面且无法合理推断的选择再向用户澄清。

## 2 全局视觉设定

下表作为目标产品的视觉设定登记模板。本仓库不设跨产品通用的品牌色、字体、主题或装饰风格；已有 Dashboard 参考库中的视觉配方仍是模块候选。

实际制作产品时，在目标项目中记录该产品的视觉设定与 token 位置。同一产品内由主控归并维护，外源和自制模块读取；不同产品可以采用不同视觉体系。官网与后台如需要不同字号或密度，使用明确的组件或区域变体。本仓库中的通用规范不自动继承某个产品的品牌。

| 设定 | 当前状态 | 后续需要记录的内容 |
| --- | --- | --- |
| 整体风格 | 待参考样式确定 | 具体视觉特征、参考来源、适用页面 |
| 明暗主题 | 待确定 | 浅色、深色或双主题，以及切换需求 |
| 颜色 | 待确定 | 页面与容器背景、文字层级、边框、强调色、状态色、图表色 |
| 字体与字号 | 待确定 | 中英文字体、回退字体、字号层级、字重、行高、数字样式 |
| 间距与密度 | 待确定 | 间距尺度、页面边距、组件内边距、控件高度、表格行高 |
| 页面框架 | 待确定 | 导航位置与尺寸、内容宽度策略、标题区、滚动方式 |
| 形状与层次 | 待确定 | 圆角尺度、描边、阴影、浮层层次 |
| 图标与动效 | 待确定 | 图标来源与风格、尺寸、动效方式与时长 |
| 组件与技术约束 | 待项目确定 | 已有组件库、实现框架及需要继承的限制 |

收到参考后，只填入其能支持的决定。截图中的精确字号、颜色值或尺寸无法直接确认时，标为“依据截图估计”，避免写成精确测量结果。已有源代码或设计文件时，以实际可核对的值为依据。

局部参考默认用于当前区块。用户说明参考代表整套产品，或要求统一全局风格时，将相关选择写入目标产品的设计记录，可采用上表结构，并记录来源和受影响模块。首个区块的临时尝试不自动成为全局规则。只有用户明确修改本系列的通用规则时，才更新本规范。

在全局设定尚未确定时，具体任务可以采用与参考一致的临时方案推进；将其记在模块记录中。没有参考的部分优先沿用已有界面，其次采用满足当前任务的简洁默认方案。

## 3 从参考样式提炼设计方法

制作一个模块前，结合用户描述和可用参考，确认要借鉴的范围，例如整体布局、表格密度、卡片层级、配色或交互。用户已经说明的内容直接执行；可合理推断的细节自行处理并在记录中区分。

按实际相关性提取下列信息，无需机械填满每一项：

| 观察维度 | 提炼内容 |
| --- | --- |
| 页面结构 | 内容分区、主次关系、导航与操作位置、阅读顺序 |
| 空间组织 | 内容宽度、对齐线、列与间距、留白分布、信息密度 |
| 字体与颜色 | 标题和正文层级、数字表达、强调方式、表面层次 |
| 组件细节 | 控件尺寸、表格结构、卡片边界、标签、图标、浮层 |
| 交互与状态 | 可观察到的筛选、展开、切换、反馈与状态变化 |
| 适用条件 | 哪类任务适合此布局，内容变多或变少时怎样调整 |

将观察转化成可复用的规则。例如“核心指标集中在首屏，并保留口径和对比周期”，比“照着这张截图摆四个卡片”更适合写进 skill。用户要求精确复现时，按其要求保留对应结构。

多份参考可以分别负责不同问题，但要有明确分工。例如采用 A 的布局、B 的表格组织，并统一到项目已有的字体和控件。避免把各自的颜色、圆角与阴影不加选择地拼在一起。

单张静态截图不能证明悬停、键盘、加载或窄屏行为；为这些状态补充合理设计时，标明它们是补充方案。参考中的业务文字、数据和标识按本项目任务替换。

## 4 共用视觉与组件规则

### 布局与信息层级

- 同一层级的页面沿用统一的导航、内容起点、标题区和全局操作位置。模块可以在主内容区采用适合其任务的布局。
- 建立清晰的主要对齐线。相邻标题、容器、表格和操作区应有可解释的对齐关系。
- 用分组表达内容关系。只有确实需要独立边界、背景或操作的内容才增加容器，避免连续套叠造成空间浪费。
- 页面主要操作应易于辨认，次要与危险操作有明确区分；不要让多个不相关操作同时争夺最高视觉权重。
- 处理真实内容的长度与数量：长标题、长名称、多位数字、多标签和内容缺失都不能破坏基本布局。

### 字体、数字与文案

- 同一语义层级复用同一套字号、字重和行高。用有限且有明确用途的层级组织标题、正文、辅助文字和数据。
- 为中英文混排、数字、单位和日期选择协调的字体与间距。表格中需要逐行比较的数字优先考虑等宽数字及一致对齐方式。
- 金额、百分比、日期、单位、精度和正负号遵循同一项目约定。区分零值、缺失值和未加载值。
- 操作文案描述具体动作，错误提示说明发生了什么及如何继续。标题和辅助文字服务于当前业务任务。

### 颜色与公共样式值

- 以用途命名公共样式值。例如颜色区分页面背景、容器背景、主要文字、次要文字、边框、交互强调和状态表达。
- 后续确定具体颜色、间距、圆角等值后，在项目中集中维护。模块优先引用这些值；沿用已有项目命名，不额外制造重复体系。
- 同一颜色不应在相邻场景中表达相互矛盾的状态。状态表达同时提供文字、图标或其他线索，保证用户不只靠颜色理解。
- 图表系列颜色保持稳定；某一指标在不同图表中尽量使用一致编码。强调色和图表色分别按用途安排。
- 文字、边界、选中状态和焦点应清晰可辨。根据实际背景检查对比，尤其关注浅色辅助文字和深色主题。

### 公共组件

- 同一种按钮、输入框、下拉框、标签、卡片、表格、弹窗和提示在不同模块中共享基础尺寸和状态逻辑。
- 需要紧凑版、常规版或其他变体时，定义命名和使用条件。各模块使用已有变体，新增变体要说明实际用途。
- 图标使用一致的来源或视觉语言。纯图标操作需要可理解的名称；含义不直观的操作提供可见文字或提示。
- 浮层和固定区域的层级应有统一安排，避免菜单被裁切、弹窗被遮挡、焦点或主要操作被固定元素覆盖。

## 5 交互状态与不同屏幕

- 为任务涉及的组件补齐适用状态：默认、悬停、键盘焦点、按下、选中、禁用、加载、成功和错误。组件无需拥有不适用的状态。
- 数据区域区分首次没有数据、筛选无结果、加载中、加载失败和权限不足，并提供与场景匹配的下一步操作。
- 表单说明必填项、字段含义和错误位置。校验失败时保留已输入内容；提交后提供明确反馈。
- 操作进行中避免重复提交。删除、批量操作等行为按实际影响提供必要确认或撤销机会。
- 关键流程可使用键盘完成，焦点可见，控件有明确名称；打开和关闭弹窗后合理安排焦点。
- 动效用于解释状态或位置变化，并考虑减少动态效果的偏好。实际时长和曲线沿用全局设定。
- 按本项目的模块分工约定，`gpt-taste` 只用于对外营销页面，不调用到 Dashboard 或业务工具。后台保留服务于任务的轻量反馈和状态转换。
- 窄屏优先保留任务所需内容和操作，按内容需求调整排列。表格可使用横向滚动、重点列或详情展开，并保持字段含义可辨。
- 明确页面与局部区域各自的滚动方式，检查固定表头、侧栏与浮层是否遮挡内容。

## 6 各模块的职责边界

以下是后续可选分工，不要求一次创建全部 skills。

| 模块 | 主要职责 | 继承的共用内容 |
| --- | --- | --- |
| 页面框架 | 导航、标题区、内容宽度和整体滚动结构 | 字体、颜色、间距、公共组件 |
| Dashboard | 指标优先级、图表选择、概览布局和数据解释 | 页面框架、卡片、数字与图表样式 |
| 数据列表 | 表格、搜索筛选、排序分页和批量操作 | 控件、密度、状态表达和数字规范 |
| 表单与设置 | 字段分组、填写流程、校验、保存与反馈 | 字体、控件、间距、提示与浮层 |
| 详情页 | 信息分组、状态、关联数据和操作入口 | 页面框架、组件与信息层级 |
| 视觉优化 | 检查当前页面并修正具体视觉与交互问题 | 已确定的项目风格和模块意图 |

skill 的独立边界以“是否有独立使用场景和处理方法”为依据。按钮圆角、某一种配色、单个行业案例等一般放入共用设定或模块参考资料。

每个模块 skill 应写清适用场景、需要的输入、设计判断方法、交付内容、相关参考和必要检查。需要参考案例、代码模板或素材时再增加相应资源。

## 7 跨窗口协作与更新

设计工作以本文件及可用的项目模块记录为共同上下文。聊天中的决定只有写入项目文件后，其他窗口才能可靠接续。原制作仓库的记录属于可选上下文，不是分发版 Skill 的运行依赖。

制作模块时，按以下顺序处理：

1. 读取本规范及已有的相关模块记录，检查全局视觉设定。
2. 阅读本次参考，提炼用户要求采用的特征，确定局部处理范围。
3. 完成当前模块的 skill 或界面成果，复用已有共用设定。
4. 在目标项目的模块记录中保存本次新增或改变的决定及实际产物位置；采用该约定时，可用 `design-system/modules/<模块名>.md`。
5. 如果本次要求明确涉及产品全局风格，更新目标产品的设计记录与 token，并说明受影响模块及实际同步情况。如果修改的是本系列的通用规则，则更新本规范的相关条目、状态、版本和更新记录。

模块记录只保留有助于后续接续的内容，可以采用以下字段：

| 字段 | 内容 |
| --- | --- |
| 模块与范围 | 本模块处理的任务及页面区域 |
| 参考来源 | 用户提供的链接、文件位置或参考说明 |
| 采用的特征 | 哪些布局、样式或交互被采纳及适用条件 |
| 共用设定 | 继承的全局决定，必要时注明规范版本 |
| 局部决定 | 只适用于此模块的变体、估计值和补充设计 |
| 全局影响 | 是否涉及共享组件或设定，哪些模块需要同步 |
| 交付与验证 | skill、示例或界面位置，已检查的行为和待处理项 |

跨窗口需要的参考应记录可再次访问的位置。只有聊天中可见的附件，不假设其他窗口也能读取；如已得到可保存的文件则归档并记录路径，否则保留足够明确的样式观察和来源说明。

不同窗口尽量编辑各自的模块记录与 skill。更新共用文件前重新读取当前内容，只修改相关条目；出现并发改动时保留其他任务已有的有效决定，并解决具体冲突。

共用规范保持一套权威规则，英文版为维护源，中文版同步更新。本版本中的 skill 引用本规范；需要单独分发时，将必要摘编随 skill 打包并注明来源版本，更新时检查副本是否需要同步。

## 8 交付检查

依据实际任务检查相关项目，无需为未涉及的模块增加工作：

- 主要任务和操作清楚，信息层级与用户需求相符。
- 对参考样式的采用能够明确说明，临时选择与全局决定区分清楚。
- 字体、颜色、间距、控件和状态符合已有共用设定。
- 长文本、大数字、内容缺失和不同数据量下布局可用。
- 涉及的空状态、错误、加载和键盘操作有合理处理。
- 涉及界面实现时检查实际渲染，以及任务要求覆盖的屏幕尺寸和主要操作；仅编写规范或 skill 时，检查规则是否明确、资源引用是否有效。
- 模块记录、实际成果和全局设定相互一致；说明尚未验证的部分，不将未执行的检查写为通过。
