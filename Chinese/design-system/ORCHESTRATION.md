# 自制与外源设计 Skills 联动方案

版本：0.4.7
日期：2026-11-21  
分发版：0.4.2，中文
状态：采用分层按需加载。[界面设计主控](../orchestration/design-orchestrator/SKILL.md) 为 1.2.7；应用框架、数据列表、Dashboard、交互及其浮层子模块、全局风格、组件库已有入口，响应式与产品参考研究已有双语入口，按实际能力接入。能力是否可用以当前发现结果为准。

本方案覆盖官网、作品集、旧站改版、参考图转页面、业务后台和设计方向探索。配合 [共用设计规范](FOUNDATIONS.md) 使用。每个设计区域选择一个主力，再按任务需要使用组件、交互、响应式和设计情报能力。

## 1 总体流程

### 三层结构

1. 核心入口只识别需求、选择子 Skill、汇总 Token 与交接；不合并业务规则，不全量加载子模块。入口原以 500–2000 个中文汉字为本项目预算，英文版保持等义与精简，不机械套用英文字符数，也不将其视作通用最佳长度；详细参考按需读取。
2. 业务能力保持独立。Dashboard 负责内容结构，交互负责行为，浮层负责对应组件选型与实现，全局风格负责视觉方向指导与 Token 生成／校验。现有名字保留，并为用户习惯的名称提供别名映射。
3. 本地 MCP 服务提供元数据目录、单个入口读取和指定资源读取。AI 根据需求调用这些工具，再应用获得的规则完成任务；协议层不自行运行模型或把 Markdown 当可执行程序。工具数量保持固定，不为每个子 Skill 重复注册一整套工具定义。

设计判断由当前执行任务的 AI 完成，MCP 只把选中规则送入上下文。查目录不返回全部正文；读一个模块不自动读取其所有参考。服务、接入和测试见 [MCP 使用说明](../mcp/skill-cluster/README.md)。每次选择一套语言目录；语言选择不改变按需加载。

核心与所选业务模块共同覆盖以下步骤，具体方法归属对应子模块：

1. **识别任务**：判断页面用途、新建或改版、目标用户、已有品牌与组件、参考用途、目标设备及交付内容。
2. **选择主力**：确定当前页面或区域由哪个 skill 主导；复用主题或主力已有的适用方向，选型未定时再按需使用全局风格指导。
3. **统一设计决定**：采用已生成的相容值，或由 `global-style-skill` 补齐缺失值与必要校验，核心汇总单一权威 Token 源；主力已覆盖时不再安排一套主题。交互、组件与响应式约定分别由对应模块负责。已有完整主题的局部修复无需重新生成 token。
4. **按分工实现**：主力负责页面结构与实现，辅助模块处理约定范围内的问题。依据实际依赖安排工作，无需固定逐个调用所有 skills。
5. **检查和交接**：检查设计目标、页面行为与项目一致性，记录实际变更及待处理事项。

新项目可先形成临时视觉草案，方向稳定后再统一 token。旧项目先读取现有 token 和组件，审计后只调整确需改变的部分。临时草案不能无记录地覆盖现有产品规范。

这里的调度是指导执行任务的 AI 按需读取和应用 skills。仅在文件中列出 skill 名称不会自动运行它；每个入口必须可定位、资源必须可读取，需要脚本的能力还需具备实际运行条件。主控不默认另开聊天或并行修改同一份代码。

主控入口职责表是当前全部入口的选择索引。先按交付物和局部范围，再按页面类别选择，只补未覆盖的能力。已有完整主题的普通局部任务无需全局风格；明确比较方向或改风格时仍可使用。主力已有行为可以满足交互与响应式要求。完整数据列表使用 `data-list-design`；共享框架变更使用 `app-shell-design`；尚无可用独立页面 Skill 的表单，由当前执行者负责页面编排／业务流程，专家补具体贡献；目录描述和上游隐式调用标志不扩大这些分工。

同一任务内复用规范入口及已读共享资源，父回链和别名不重启流程。来源变更、上下文缺失或需要新指导时再读；MCP 仍是无状态读取器。整页溢出裁切、浮层语义等具体冲突处理见 [适配指南](../orchestration/design-orchestrator/references/skill-adapters.md)。

## 2 独立子模块的职责

实际名称与入口由目录发现，不把旧状态写成永久可用性声明。`dashboard-skill`、`interaction-skill`、`floating-component-skill` 分别映射到现有 `dashboard-design`、`interaction-design`、`floating-components`。

| 模块 | 核心职责 | 介入时机 | 边界 |
| --- | --- | --- | --- |
| 主控 `design-orchestrator` | 识别任务、选择子模块、汇总 token 与交接 | 任务入口与分工变化时 | 不包含业务细则，不默认加载全部参考 |
| 全局风格 `global-style-skill` | 推荐／比较视觉方向；生成、扩展、迁移或校验项目 token | 选型未定、明确改风格、Token 缺口或所需校验 | 咨询可停在 Token 之前；不接管页面，不重复主力已完成的适用选型；主题完整的普通局部任务跳过 |
| 产品参考研究 `design-reference-research` | 查找和比较具名产品案例；核查来源范围并返回可迁移模式 | 明确要求案例研究／比较、来源核查或具体借用特征缺少依据 | 仅用名称传达氛围且方向依据充分时无需研究；区分营销／产品／演示界面和证据类别；不接管页面或创建第二个 Token 源 |
| 浮层 `floating-components` | Tooltip、Toast、Alert、Modal、Popconfirm、Drawer 的选型和实现 | 当前任务涉及浮层或消息时 | 直接使用交互包内现有子入口，不复制第二套规则 |
| Dashboard `dashboard-design` | 业务角色与任务、指标和图表、信息密度、看板内容结构 | 后台需求分析与实现阶段 | 负责仪表盘内容区及摘要，沿用页面框架；独立全站导航、全量列表和表单另行处理 |
| 数据列表 `data-list-design` | 信息优先级、搜索筛选、视图与列、排序分页、选择、批量任务、导出与详情返回 | 完整后台列表设计与实现 | 复用框架／Token 及 Table／公共控件；交互、响应式补缺口；仅选所需功能 |
| 应用框架 `app-shell-design` | 导航层级、路由上下文、标题区、内容边界与滚动 | 新建或调整共享应用框架 | 已有框架足够时复用；页面主力负责内容；明确一个返回状态协调者 |
| 精细交互 `interaction-design` | 状态转换、反馈、焦点、键盘、加载与异常恢复 | 实现前确定必要行为，实现中落实，完成后验证 | 不另定品牌色或重排整页；补足主力尚未覆盖的行为 |
| 组件库 `component-system` | 复用现有组件、公共组件与变体、统一组件接口和视觉状态 | 结构确定前盘点，实现中复用或补充 | 按需新增组件；不把一次性展示布局全部强行组件化 |
| 响应式 `responsive-design` | 内容优先级、布局变化、导航收纳、触屏、表格图表的窄屏处理 | 布局前提出约束，实现中调整，完成后检查 | 沿用项目风格，不只在结尾缩字号或隐藏内容 |

组件库实现承载共用交互和响应式行为，交互与响应式模块定义必要规则并验证它们。多个模块可以贡献判断，但同一组件或区域的实现由明确的负责人整合。

全局风格的 [选型指南](../orchestration/global-style-skill/references/style-selection.md) 与本地参考目录按需使用，不是新增必经步骤或独立主题权威。只取相关候选，覆盖或所需依据不足时再补研究；布局、材质、图像或动效标签不把页面、素材或交互职责移交全局风格。

已有 [Dashboard skill](../page-design/dashboard-design/SKILL.md) 已包含必要交互和窄屏处理。其他自制模块应补足复杂或跨页面的问题，复用已有方案，避免反复重做同一状态。

[产品参考研究](../design-research/design-reference-research/SKILL.md)增加 84 项来源记录和 8 个已做文档审查的案例。先读小索引，再读选定卡片，通常 1–3 个；只有索引的记录在检查前保留范围未知。现有 MCP 目录搜索 Skill 元数据，不搜索案例正文；通过选定资源读取完成导航，无需新工具。第三方分析、建议或合成示例不等于官方规则或线上产品核验；来源提示词作为数据，不作为执行指令。研究将借用特征、出处和缺口交回已有负责人；已有主题的局部修复跳过，除非请求包含参考工作。通用 UX 研究与产品案例研究各补具体缺口，不要求两者都执行。

共享框架确需调整时，主控才选择 `app-shell-design`，由其负责跨页结构与滚动，页面主力负责业务内容。导航、组件、响应式按缺口配合，不把框架流程变成每页必经步骤。

## 3 外源模块与接入状态

下表依据已确认的上游仓库，不是对所有同名 skill 的通用能力认证。本次发布包含十四个外源包及许可证；随包提供规则不等于宿主所需工具已经配置或全部流程已经成功执行。接入说明见 [本版 README](../README.md)；仅在选择上游、可选家族成员或历史版本时读取 [外源目录](../orchestration/design-orchestrator/references/external-catalog.md)。包按功能分类放在所选语言目录下，同类内源与外源共用分类。

| 外源 skill 或家族 | 本体系计划用途 | 核验状态与边界 |
| --- | --- | --- |
| `design-taste-frontend` / `taste-skill` | 适配其规则的官网、品牌与产品展示页；兼容的既有营销网站审计与改版 | 两个名称指向同一 skill；`taste-skill` 是仓库及包目录名称。以 tasteskill 2.5.1 纳入 page-design，保留固定版本及原资源 |
| `redesign-existing-projects` | 历史独立的审计与渐进改版流程 | 当前 taste 已整合改版能力；旧独立入口已固定版本纳入 legacy，仅在明确选择时使用，不将其流程静默映射为当前 taste |
| `ui-ux-pro-max` | 补充缺失的风格、字体、配色与 UX 依据，形成候选方案 | 已随 Python／数据依赖纳入 design-research；只负责研究与建议，本地选型后不自动再跑一次 |
| Classics：`gpt-taste`、soft、minimalist、brutalist、Stitch 与旧 taste 变体 | 可选的高表现力、特定风格、工具专项或历史流程 | 已从 `taste-skill-classics` 纳入 visual-styles、tool-integrations 与 legacy；只在用户明确选用时启用，`gpt-taste` 不用于 Dashboard 或业务工具 |
| 视觉参考：`imagegen-frontend-web`、`imagegen-frontend-mobile`、`brandkit` | 生成视觉参考或品牌板 | 已从 `imagegen-skills` 纳入 image-design；图片产物不等于已实现的页面或权威产品 token |
| `image-to-code` | 先生成参考图，再分析并实现前端代码 | 随包入口为 `image-design/image-to-code`，上游入口为 `imagegen-skills/skills/image-to-code`；用户提供的旧 taste 路径属于历史位置，不自动重新生成用户已有的目标图 |

Classics 入口禁用隐式调用。泛泛要求“页面更有视觉冲击力”不等于允许自动加载其中一个。用户点名调用或本次上下文已有明确授权时，核对实际入口与依赖，并遵守已分配范围。目录列名不构成安装授权；当前入口缺失也不自动回退到历史版本。

### 本机 design taste 的具体约束

当前已读版本包含配色和字体生成、布局与素材流程、首屏与段落动效、组件和响应式约定，以及自身的浏览器检查。它还要求保持生成的 `:root` 块，并有特定的整屏布局和动效规则。因此不能直接把它当成只产出中性骨架的工具。

接入方式根据实际任务选择：

- **完整使用**：其规则与项目目标相容时，由它主导页面；主控把采用的样式值登记到本项目规范，复用它已有的交互和响应式能力。
- **局部借鉴**：项目已有品牌或结构与其流程不相容时，明确采用其中哪些可复用的设计方法或资源。记录这是适配使用，按实际项目目标检查结果。
- **切换主力**：它的必需规则与任务核心目标冲突、且无法通过支持的配置解决时，选择其他适合的主力完成该区域。

只修改外部 CSS 不能保证内部检查也接受新的设计。不要通过删除第三方检查或修改其工具文件伪造通过；完整使用和局部借鉴分别报告实际验证范围。

## 4 五种场景的推荐路由

### A 新建官网或作品集

主控识别目标与素材 → 选择当前可用且兼容的主力，通常评估 `design-taste-frontend` → 复用其适用方向，选型未定时再使用全局风格指导 → 主控整理本项目 token → 主力结合组件、交互和响应式要求实现 → 检查结果。候选或依据仍有缺口时才补研究。

一般品牌或产品展示可优先评估 `design-taste-frontend`；只有用户明确选用 `gpt-taste` 或其他 Classics 技能或流程，且实际版本适配参考和区域时才使用。表现力诉求本身不能覆盖上游禁止隐式调用的约定。

高表现力构图会影响内容顺序、素材与布局，应在设计阶段确定。仅需要某个区域增加效果时，可以限定辅助者的区域、行为、性能与减少动态效果要求。不要默认先做完整官网，再用另一个完整流程重做一遍。

### B 旧网站改版

主控读取现有品牌、代码、token 和组件 → 选择当前可用且兼容的主力审计与改版 → 主控确定保留项和改动范围 → 按区域改造 → 相关模块补足组件、交互与响应式 → 检查一致性与已有关键流程。

当前 `design-taste-frontend` 已包含适用营销网站的改版能力，使用前检查其默认要求与已有品牌的兼容性。历史独立 `redesign-existing-projects` 仅在明确选用、固定版本且已安装时作为选项；不依赖已移除入口，也不替换成当前 taste 后声称执行了旧流程。

涉及 Dashboard 的区域交给 `dashboard-design`。单纯调整字号和间距时，不必启动全部自制模块。旧项目的公共规则发生变化时，检查受影响的共享组件，避免只修当前页面。

### C 设计稿转前端页面

主控先确定参考用途 → 提取或映射 token → 选择能够检查所给图片的可用实现者 → 结合已有组件实现 → 补足参考图未提供的必要交互和窄屏方案 → 按用途检查。

当前 `image-to-code` 已从 taste 迁移到 `imagegen-skills`，流程为生成参考图 → 分析 → 实现。用户需要这种先出图再编码的创作流程、且依赖可用时才选用。忠实还原已有图片时，继续以该图为目标，不自动替换成新生成的设计。由选定的读图实现者完成，或明确说明仅借鉴相关方法，不声称原样执行了外源完整流程。

两种用途需要在实现前分清：

- **忠实还原**：参考图是视觉依据。主控从图中提取项目样式，检查实现相对参考的偏差；保留用户要求还原的颜色、间距与形状。
- **融入现有产品**：参考用于布局或指定局部。实现前将参考中的视觉角色映射到现有 token，检查它与项目规范的兼容性。

若“忠实还原”与既有品牌要求发生实质冲突，先用用户的明确要求判断优先级；仍无法判断时，只询问这一项取舍。不能先宣称精确还原，再在末尾擅自换成另一套品牌。

检查对象包括布局、颜色、字体、间距、圆角、组件复用与遗漏状态。是否存在杂乱配色或间距应依据具体产物判断，不把它写成某个未核验 skill 的必然缺陷。

参考图若属于 Dashboard，主控还应使用 `dashboard-design` 检查指标含义与业务结构；还原主力只负责约定范围，避免两者争夺页面结构。

### D 新建 Dashboard 或管理面板

主控明确角色与业务任务 → `dashboard-design` 确定内容结构并提出所需视觉密度 → 继承适用方向，选型未定时才使用全局风格 → 主控整理后台 token → Dashboard 与组件库完成布局和组件 → 按已约定的交互、响应式要求实现与检查。候选或 UX 依据仍有缺口时才加入 `ui-ux-pro-max`；主力已选的适用方向和值直接复用。

后台的交互和窄屏要求应在实现前确定。已有项目直接复用其公共组件与 token；新项目只创建当前页面需要的组件。需要变更的框架交给 `app-shell-design`，仪表盘保留内容职责；明确路由／标题插槽、滚动容器和返回责任。

遵守用户明确要求：不调用 `gpt-taste` 处理 Dashboard、管理工具或内部业务区域。允许服务于任务的轻量反馈、展开和状态转换，不将此限制扩大成“后台不能有任何动效”。

`ui-ux-pro-max` 在此场景提供候选设计或 UX 建议，不负责后台页面代码，也不直接覆盖已选 token。

### 完整数据列表

由 `data-list-design` 负责完整列表区域，复用产品框架、权威 Token 与已有 Table／控件；交互和响应式只补未覆盖的行为。列表主力定义查询、选择、批量任务和导出范围，并检查空结果、权限、部分失败和详情返回连续性。每个组件实现保留一个负责人；完成依据见[列表场景](../orchestration/design-orchestrator/references/scenarios.md#完整数据列表)。

### E 没有灵感，寻找设计方向

主控整理受众、业务、现有品牌和参考偏好 → `global-style-skill` 按需使用本地参考推荐或比较方向 → 候选／依据仍有缺口时再补研究 → 交付所需建议，或在任务要求时形成设计约定与 Token。

沿用已有主题／参考，除非用户明确要求变更。新项目信息充分时直接作出有依据的暂定选择并继续；只有重大取舍确实无法推断时，才展示两到三个具体选项，不要求每次任务都询问风格。纯咨询停在建议，不应用主题或编写页面代码。

### 具名产品参考

区分氛围描述、具体视觉借鉴，以及明确要求的案例研究／比较、来源核实或忠实还原。名称仅传达氛围且方向依据充分时，无需自动研究，也不虚构来源细节。具体借鉴或还原先检查所给证据；缺失的来源依据，以及明确要求的研究／比较／审计交给 `design-reference-research`。迁移特征前先确认真实界面范围和证据类别；营销后台截图或生成的 SaaS 示例不能证明产品工作流。保留页面主力、当前品牌与 Token 权威来源。来源只有索引时，先核查再推荐具体特征，或说明尚不可得的内容。使用[参考场景](../orchestration/design-orchestrator/references/scenarios.md#产品参考研究与迁移)检查这些区别。

用户要求时，适配后的项目 `DESIGN.md` 记录已采用特征、来源、区域范围与补充行为决定，并链接真实 Token 源。准备文档不创建第二套独立可编辑主题、不运行 Stitch，也不证明界面渲染成功。

### 混合场景与小任务

同一产品同时有官网和后台时，按页面或区域路由。品牌色等可以共享，营销排版和后台密度使用明确命名的变体。官网可用的强动效不能经共享组件蔓延到后台。

一次只修表格溢出、弹窗焦点或按钮状态时，直接使用相应模块处理。路由按当前任务变化，不按“已安装哪些 skills”决定全量加载。

## 5 Token 和设计决定的归属

每个实际产品项目保留一处可维护的 token 来源。全局风格按需负责生成、迁移和校验，主控负责选择并汇总结果；其他模块产生的相容值也可以成为该来源。已有主力完成所需决定和检查时，不重新生成，也不强制再走一遍全局风格／研究流程。

- 复用项目已有主题变量、组件库主题或设计 token 文件，避免为了本体系额外生成第二套值。
- 没有现成机制时，在实现框架内建立一份 token 文件。将它的位置、已定视觉方向和变体规则写进目标项目的设计记录。
- 共用值按用途定义，例如页面背景、主要文字、强调色、边框、间距和圆角。新值先检查现有值与组件变体能否满足。
- 营销页面、应用页面、紧凑表格等必要差异以明确作用域或组件变体表达；不要让同一全局名称在不同模块被悄悄重定义。
- 外源自身有生成机制时，采用、映射或替换其中一种维护方式，并说明实际权威来源。避免两套可独立修改的配置互相漂移。
- 规范校验检查不符合既定决定的偏差；用户明确采用的新方向通过记录变更进入项目，不机械退回旧样式。

本 skills 仓库保存通用方法、参考库和模块能力。不同真实项目可以采用不同品牌、字体和主题，不把某次客户项目的 token 写成整个 skills 系列的永久默认。

## 6 交接内容与外源适配

每次任务传递足够简短且具体的工作约定，记录在现有任务或项目文档中即可，无需为每个步骤增加独立文件：

| 信息 | 要写清什么 |
| --- | --- |
| 任务与区域 | 做哪一页、哪一部分，用户要完成什么 |
| 主力与辅助 | 谁负责结构和实现，谁只提供研究或局部补足 |
| 设计依据 | 当前 token 的位置、参考用途和选定视觉方向 |
| 组件与行为 | 使用哪些现有组件，需补哪些状态或组件变体 |
| 设备与动效 | 目标设备、布局变化和允许的动效范围 |
| 输出与检查 | 期望交付物、可修改范围、需要验证的具体结果 |

多区域或共享变更时，在已有记录中把相关决定对应到整合负责人、实现位置、实际检查／证据及未验证项。同一执行者可以承担所有职责，单人完成也适用。交付前按变更选择检查：主题实际使用、受影响调用处的公共组件行为，以及重排后的阅读／键盘顺序。复用适用证据，记录覆盖范围并补缺口，不自动重跑专家流程或审查全站。生成主题不能单独证明使用正确。[交接约定](../orchestration/design-orchestrator/references/design-contract.md)提供简短记录及变更触发条件。

收到外源入口后，读取实际 `SKILL.md` 和当前任务所需资源，核对版本、输入输出、依赖、默认样式及检查方式。确定完整使用、局部适配或仅作参考，再用于本项目。

不要假设每个外源都支持“只研究”“仅组件”之类的执行模式。本方案约定的是使用范围；若原文件无法按该范围工作，提取适用资料作为研究依据，或选择其他可用方法，不声称已执行其不存在的模式。

外源未安装或暂不可读取时，保留候选位置，并在实际执行中用可用能力推进。不得声称已经调用或验证缺失的 skill，也不为当前方案安装来源不明确的同名包。

后续在不同窗口制作自制 skill 时，先读取共用规范和本方案，再确定该 skill 的输入、输出、职责及接续点。模块成果按现有约定记录到 `design-system/modules/`。跨窗口通过文件接续；并行实现时划分文件范围，由主控合并公共修改。

## 7 建议制作顺序与验证

主控、app-shell-design、Dashboard、data-list-design、精细交互及浮层、全局风格、组件库、响应式、design-reference-research 均有独立双语入口。十四个外源包按功能分类纳入；保持正文独立，按任务发现相关入口，不全量加载技能库。

每个模块都需要能独立使用。在其他自制 skill 尚未完成时，按共用规范补足当前任务，不能因为推荐依赖缺失而停下普通页面工作。

用以下请求检查主控是否选对主力和边界：

| 请求 | 应观察到的结果 |
| --- | --- |
| 新建简洁企业官网 | 先选择方向与合适主力，不自动叠加第二套完整创意流程 |
| 为已有紫色品牌官网改版 | 保留用户品牌要求；发现外源默认色限制时进行适配或换主力 |
| 精确还原一个截图 | 检查并实现所给截图，不自动重新生成目标图或替换参考配色 |
| 做一个视觉冲击力强的营销页 | 选择可用主力，不隐式调用需要用户选用的 Classics |
| 使用 taste-skill | 仅解析为 `design-taste-frontend` 一次，不创建重复 skill |
| 给后台做经营概览 | 使用 Dashboard；不调用 `gpt-taste`；早期确定状态与窄屏策略 |
| 官网首页加后台订单列表 | 列表交给 `data-list-design`，营销交给合适主力；复用品牌与组件，避免营销动效影响业务区 |
| 只修手机上的表格溢出 | 局部处理响应式，不重做全站 token 或页面风格 |
| 只想要三个设计方向 | 交付候选和推荐，不自动生成整站代码 |

以上是持续可用的行为验证场景。已执行的检查及具体范围记录在制作项目的模块记录中；历史研究档案不属于运行依赖，也不随发布包附带。随包提供以及文件／协议检查不等于全部外源设计流程已完成端到端执行。
