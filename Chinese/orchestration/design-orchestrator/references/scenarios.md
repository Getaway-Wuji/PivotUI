# 场景路由

先看交付目标与改动范围，再看页面用途。需要实现时，以下路线是执行分工，不是只交一张流程表。候选 skill 均须先核对当前是否可用。

## 判断顺序

1. 只要方向或审计：交付相应结果，不自动写页面。
2. 只修一个明确问题：按局部能力处理，不重新选整站风格。
3. 指定设计图：先确定还原目标；精确还原可以成为视觉依据，即使页面已有品牌。
4. 剩余工作按营销展示与业务使用划分，再结合新建或改版选主力。改版是工作方式，业务用途决定内容区域由谁负责。

一个请求可涵盖多个区域。每个区域分别确定主力、参考依据、共享部分和局部变化，不强行用一个分类套完整产品。

## A 新建官网或作品集

判断受众、主要行动、品牌素材和表现诉求；沿用所选主力已有的适用方向。选型仍未确定时才按需使用全局风格指导，候选或依据仍有缺口时再补研究。普通企业、产品展示可评估 `design-taste-frontend`；其包名 `taste-skill` 是别名，不是另一套流程。只有用户点名或上下文已有明确授权、且检查相容时，才使用 `gpt-taste` 或其他 Classics 入口。泛泛要求视觉表现力不构成隐式调用需明确选用的 Classics 的依据。以实际 skill 版本和用户参考判断适合程度。

主力先形成方向与内容结构，主控归并可用 token，再结合组件、交互和响应式完成实现。若外源自身生成一套相容的 token，可以采用它作为本项目权威来源，不再复制出另一套独立可改的颜色表。

非对称构图、滚动叙事和大幅动效会影响页面结构，应在设计时决定。仅增加一个区域的效果时才使用明确限定的辅助任务，并约定减少动态效果下的展示、窄屏行为和性能需求。

**完成依据**：页面传达清楚、素材与内容匹配、各区域风格一致、目标设备可用。主力自带的交互与响应式已满足要求时，不必再运行完整辅助流程。

## B 旧网站改版

先读取现有页面、公共组件、样式和关键交互。当前 `design-taste-frontend` 声明适用于评审与改版；先核对具体流程是否相容，不假定存在独立审计模式。原独立 `redesign-existing-projects` 只有在明确选用、固定版本且已安装时才可主导。不依赖已移除的当前入口，也不替换成当前 taste 后声称执行了旧流程。主控据此确定应保留的品牌与功能，以及要改变的层级、间距、颜色或其他问题。

需要改造的 Dashboard 内容由 Dashboard 能力处理，完整业务列表交给 `data-list-design`；共享应用框架的变更交给 `app-shell-design`；尚无可用专门页面 Skill 的表单由当前执行者负责页面编排与业务流程。组件、交互能力提供限定范围的实现支持。只修当前页面时，不擅自更换框架、重建所有组件或改写整个品牌。

**完成依据**：审计中选定的问题得到改善，公共改动影响已检查，原有主要流程可用。用户只要审计时，交付有证据和优先级的发现即可。

## C 设计图转页面

先读取图片及用户说明。只有确实需要精确还原且缺少目标图时才索取图片；不能用想象填补未见参考并声称还原。

| 目标 | token 与实现的处理 | 检查依据 |
| --- | --- | --- |
| 忠实还原 | 从参考提取视觉角色与数值，估计值如实标明；复用组件时保持要求还原的表现 | 在目标尺寸对照参考，检查结构、字体、颜色、间距与形状 |
| 融入现有产品 | 借鉴指定结构或局部，在实现前映射到项目 token 与组件 | 检查参考采用范围，以及现有品牌和组件的一致性 |

用户明确说“照图”时按忠实还原处理；明确说“保留品牌、只借鉴布局”时按融入处理。两项强制要求实质冲突且无法判断优先级时，只澄清这一处；其余独立工作继续。

选择当前能够读取并实现所给图片的实现者。随包 `image-to-code` 位于 `image-design/image-to-code`（上游为 `imagegen-skills/skills/image-to-code`），先生成参考图，再分析与实现；任务需要先出图再编码、且依赖可用时才选择这条流程。不自动重新生成用户已有的还原目标。只借鉴其中相关方法时，记录为适配使用，不声称执行了完整外源流程。

组件能力负责复用与适配，交互和响应式能力补足静态参考未呈现的行为。截图不能证明加载、键盘、触屏或窄屏状态，这些作为补充设计处理。

后台参考中，忠实还原任务以还原者负责指定视觉，Dashboard 能力只检查业务语义和必要状态，不另换构图；按参考重新设计后台时，由 Dashboard 主导结构，还原能力只处理约定局部。无实际业务数据时标明示例，不能把图中数字视为真实业务。

## D Dashboard 与管理面板

已有完整主题的普通局部任务，不另加全局风格步骤或重新选择视觉配方。明确要求比较方向或改风格时，即使 Token 完整也可以使用全局风格；实际 Token 缺口和明确校验请求同样可以触发。Dashboard 主力已有适用方向时直接复用。

明确使用角色、核心问题、主要指标与任务、数据口径和目标设备。`dashboard-design` 负责仪表盘信息结构、指标图表和摘要区域，先提出适用的密度与层级，再继承或确定产品 token。

已有导航和页面框架优先沿用。框架本身需要新建或修改时，由 `app-shell-design` 负责跨页层级、路由上下文、内容边界与滚动归属；页面主力继续负责内容。后台并非每一页都是 Dashboard：独立订单列表、设置表单等不因位于后台而强行套指标卡片流程。

候选覆盖或所需 UX 依据不足时才使用 `ui-ux-pro-max`，只获取研究和建议。参考库中展示看板的营销图片不能代替后台设计方法。Dashboard 与组件能力落实页面，交互与响应式在实现前明确状态、筛选范围、刷新、键盘和窄屏策略。

不将 `gpt-taste` 调配到后台、内部工具或业务操作区域。用户喜欢的视觉特征可以通过现有能力实现，任务反馈、展开和状态过渡按需要保留。

**完成依据**：信息支持角色判断，指标有意义，筛选与内容一致，真实数据与示例有区分，关键操作和目标设备可用。

## 应用框架与页面连续性

共享框架需要调整时使用 `app-shell-design`。页面实现前明确路由元信息、标题／操作插槽、内容宽度／内边距和真实滚动容器。已有框架足够时，不另走框架流程。

与 `data-list-design` 配合时，由列表负责查询、页码、选择和结果有效性。指定一个负责人在相关内容就绪后协调返回顺序，保留约定的页面／局部滚动位置，将焦点恢复到稳定记录或合理回退位置。见[交接约定](design-contract.md#框架与页面返回职责)。

**完成依据**：在真实框架中验证共用的“列表→详情→编辑→后退”流程，包括记录被编辑后移出筛选结果的情况。独立模块样例通过，不等于组合后的恢复行为已验证。

## 完整数据列表

完整订单、客户、资产等后台列表由 `data-list-design` 负责列表区域，沿用产品框架与 Token。主力确定字段优先级、查询与结果布局、所需视图／列控件、选择和导出范围、详情返回；不要求每页具备全部功能。`component-system` 负责 Table 和公共控件实现，交互、响应式模块只补已识别的缺口，每个组件保留一个实现负责人。

**完成依据**：区分当前页选择和全部查询结果，处理空结果、权限限制及批量部分失败，从详情返回后恢复约定的查询、页码和位置。在运行界面中检查实际文字对比、键盘焦点和窄屏字段可达；仅有规格不能证明运行成功。

## E 寻找设计方向

从业务目标、受众和已有材料中整理约束。`global-style-skill` 可以只推荐或比较方向，无需生成 Token 或页面代码；按需读取自身选型指南和相关本地参考。候选或依据仍有缺口时再由 `ui-ux-pro-max` 或可用研究能力补充；一个流程已经回答问题时，不要求两个都运行。

沿用已有品牌及参考范围，除非用户要求变更。新项目信息充分时直接作出有依据的暂定选择并继续，不把选型变成必答问卷。重大取舍确实无法推断时，展示两到三个具体选项及实际差异；用户已有明确偏好时按偏好执行，并检查它在所需区域的适用方式。

用户要视觉草图且工具可用时，从外源目录选择对应网页、移动端或品牌板入口。产物记录为参考图片，不视为可运行界面或已采用的 token 系统。特定风格的 Classics 仍需用户明确选用。

用户只要候选时不擅自把某一候选写成已确认品牌；允许暂定推荐并说明理由。要求落成规范时，再将采用的方向变成具体设计约定和可实现的 token。不自动生成整站代码。

### 风格调度的区别场景

| 请求 | 路线及停止位置 |
| --- | --- |
| 新建供员工每天高频使用的桌面运营后台，外观由你选择 | Dashboard 主力先确定任务结构和密度；方向未定时按需使用全局风格指导，选择适用的暂定方向并继续；不例行询问、不全读卡片、不自动增加研究步骤 |
| 将当前页面做得柔和、极简 | 由现有主力／全局风格按需在所需范围落实这些特征，不因此授权调用 `high-end-visual-design` 或 `minimalist-ui` |
| 产品 Token 完整，但要求全产品改成指定的新视觉方向 | 允许全局风格选型／迁移，保持明确的 Token 权威来源并协调受影响负责人；已有完整 Token 不取消明确改版要求 |
| 比较两种适合该工具的方向，暂不实现 | 全局风格给出建议并按需取参考，只在具体缺口出现时补研究；解释取舍后停止，不改 Token、不写页面代码、不运行外源创意流程 |

## 产品参考研究与迁移

具名产品比较和来源核查直接交给 `design-reference-research`；全局风格或页面主力也可因具体证据缺口使用它。先从包内元数据开始，通常读取 1–3 个相关案例，再把决定交回当前负责人。范围与证据质量比品牌知名度更重要。检查路由时使用以下场景：

| 请求 | 路线及完成依据 |
| --- | --- |
| 为开发者工具官网比较 Linear 与 Notion，只要建议 | 检查两者营销案例，比较具体表面、字体与内容关系，注明出处；停在 Token 和页面代码之前 |
| 按 Linear 的感觉做运营 Dashboard | `dashboard-design` 继续负责；明确随包 Linear 案例属于营销证据。只借鉴适用视觉特征，业务状态和数据行为由现有模块补足；不声称取得完整 Linear 工作台规范 |
| 根据目录示例忠实还原 SAP 的真实业务应用 | 检查示例出处。演示 SaaS 界面不是品牌原生产品证据；忠实还原应使用用户提供或可访问的真实产品参考。缺失时说明缺口，并区分提出的适配方案 |
| 主题完整，只修手机表格溢出 | 使用局部响应式／页面负责人和现有主题；跳过案例研究与 Token 重建，除非请求另含具名比较 |
| 使用只有索引记录的具名来源 | 定位固定版本来源，在推荐特征前核查范围，准确记录新检查的证据。来源不可访问时说明限制，使用可用方法继续获准工作；索引本身不证明设计细节 |
| 将 Airbnb 启发的列表用于中文长标题和窄屏 | 用市场平台案例参考结构与信息关系；保留产品主题，适配中文排版，定义缺失的加载、错误、键盘与窄屏行为。在实现中验证，不声称来源已经完成 |
| 把已采用案例决定写成项目 DESIGN.md | 记录范围、选定特征、出处和补充决定，链接已有 Token 权威来源；文档交付不擅改品牌，也不自动运行 Stitch |

来源文档或场景推演只能证明研究／路由过程。视觉提升、响应式成功和交互可用需要检查实际生成页面。没有适用案例也是有效研究结果；沿用既有产品规则继续，不强配某个品牌。

## F. 图像概念与工具专项文档

按所需产物选择：网页区块图用 `imagegen-frontend-web`，应用屏幕／流程图用 `imagegen-frontend-mobile`，品牌板用 `brandkit`。保留要求的数量和格式，例如三屏应用交付三张图。承诺图片产出前检查实际生图工具；拟用提示词或文字说明不等于已生成图片。只要图片时，不增加前端编码、项目 Token 采纳或完整风格流程。

用户明确选用 `stitch-design-taste` 时，区分其 `DESIGN.md`、Stitch 生成屏幕和可运行 HTML。上游的 Stitch MCP 是可选项，检查实际 Stitch 访问，不因缺该连接就认定完全不能访问。整个工具不可用且用户接受普通 HTML 时，由页面执行者完成 HTML，不只为取得可选连接而停下，也不声称 Stitch 已运行；仅借鉴文档指导时注明范围。

## 混合场景与局部修复

官网和后台可共享品牌色、图标或基础组件，同时使用不同的排版、密度和动效范围。为每个区域指定主力，限定改动范围；营销效果不能通过公共组件默认进入业务区域。

手机表格溢出优先使用响应式能力；弹窗焦点和提交反馈使用交互能力；统一按钮变体使用组件能力。相应 skill 缺失时，按项目规范直接解决该问题，不用无关的完整页面 skill 代替。

缺失能力、版本冲突与后续模块接入的处理见 [能力发现与适配](skill-adapters.md)。

同一任务内复用已读父规则与共享规则。例如，为已有主题的表格加删除 Modal，需要浮层及相关提交／恢复指导，不必连带加载全部交互兄弟模块、生成新 Token、重设计表格或再走一遍响应式流程。新要求出现真实缺口时，只增加该项贡献并交回既有代码负责人。
