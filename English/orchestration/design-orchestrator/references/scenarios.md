# Scenario Routing

Start with the deliverable and change scope, then the page purpose. For implementation requests, these routes allocate work rather than replace delivery with a flowchart. Verify candidate availability before use.

## Decision order

1. Direction or audit only: deliver that result without automatically writing a page.
2. One specific issue: use the relevant local capability without reselecting the entire site's style.
3. Specified design image: establish the reproduction goal first. Exact reproduction may be the visual authority even when a brand already exists.
4. Divide remaining work into marketing and business use, then select leads for new builds or redesigns. Redesign describes the working method; business purpose determines ownership of content regions.

A request may cover several regions. Assign each its own lead, reference authority, shared elements, and local differences rather than forcing the whole product into one category.

## A. New marketing site or portfolio

Establish the audience, primary action, brand assets, and expressive goals. Reuse an adequate direction from the chosen lead; use global style's on-demand guidance if selection remains open, adding research only for unresolved candidate or evidence gaps. Consider `design-taste-frontend` for company and product sites; its `taste-skill` package name is an alias, not another workflow. Use `gpt-taste` or another classics entry only after a named invocation or existing explicit user authorization and a compatibility check. A general request for expressive visuals does not permit implicit invocation of opt-in classics. Judge fit from the actual version and user references.

The lead establishes direction and content structure; the orchestrator consolidates usable tokens; implementation incorporates component, interaction, and responsive requirements. A compatible token system generated by the external lead may become the project's authoritative source. Do not duplicate it as another independently editable color table.

Asymmetric composition, scroll storytelling, and substantial motion affect structure and should be decided during design. Use a narrowly scoped supporting task only for adding effects to a specific region, with reduced-motion presentation, narrow-screen behavior, and performance requirements.

**Completion evidence:** clear communication, appropriate assets and content, consistent regional styles, and usability on target devices. Do not repeat a full supporting workflow when the lead already satisfies interaction and responsive requirements.

## B. Existing-site redesign

Read current pages, shared components, styles, and key interactions first. Current `design-taste-frontend` declares review and redesign applicability; inspect its concrete workflow for fit before assigning it, without assuming a separate audit mode. The former independent `redesign-existing-projects` may lead only when explicitly selected, pinned, and installed. Do not require a removed current entry or claim the old workflow ran after substituting current taste. The orchestrator determines which brand and functional elements to retain and which hierarchy, spacing, color, or other issues to change.

Use dashboard capabilities for dashboard content and `data-list-design` for complete business lists. Assign shared application-frame changes to `app-shell-design`. For forms without an available dedicated page skill, the current implementer owns page composition and business flow. Component and interaction capabilities supply scoped implementation support. A single-page fix does not authorize changing the framework, rebuilding every component, or rewriting the whole brand.

**Completion evidence:** selected audit findings are improved, impacts of shared changes are checked, and primary existing flows remain usable. For audit-only requests, deliver evidence and prioritized findings.

## C. Build from a design image

Read the image and user instructions first. Request an image only when faithful reproduction requires a missing target. Do not invent an unseen reference and claim to reproduce it.

| Goal | Tokens and implementation | Validation basis |
| --- | --- | --- |
| Faithful reproduction | Extract visual roles and values; label estimates; retain the required appearance when reusing components | Compare structure, typography, color, spacing, and shape with the reference at target dimensions |
| Integration into an existing product | Adopt specified structure or details; map them to project tokens and components before implementation | Check the adopted reference scope and consistency with the existing brand and components |

Treat an explicit "match the image" request as faithful reproduction. Treat "retain the brand and borrow only the layout" as integration. If two mandatory requirements materially conflict and their priority cannot be inferred, clarify only that conflict while continuing independent work.

Choose an available implementer able to inspect and implement the supplied image. Bundled `image-to-code` lives in `image-design/image-to-code` (upstream: `imagegen-skills/skills/image-to-code`) and generates references before analysis and implementation; select that pipeline when the task requests image-first creation and its dependencies are available. Do not automatically regenerate a supplied reproduction target. If borrowing only relevant guidance, record adapted use rather than claiming the full external pipeline ran.

Component capabilities handle reuse and adaptation; interaction and responsive capabilities supply behaviors absent from static references. A screenshot does not prove loading, keyboard, touch, or narrow-screen behavior; treat these as supplementary design.

For faithful dashboard reproduction, the reproduction lead owns the specified visuals. Dashboard capability checks business meaning and necessary states without changing the composition. For a dashboard redesign inspired by a reference, the dashboard lead owns structure and reproduction capability handles agreed details. Label sample data; numbers in an image are not verified business data.

## D. Dashboard or management panel

Establish user roles, core questions, metrics and tasks, data definitions, and devices. `dashboard-design` owns dashboard information structure, metric charts, and summaries. It proposes appropriate density and hierarchy, then inherits or establishes product tokens. A complete existing theme needs no new selection or global-style pass for ordinary local work. Global style may participate in an explicit direction comparison or restyling request even when tokens are complete, as well as actual token gaps or requested checks. Reuse a suitable direction already selected by the dashboard lead.

Reuse navigation and application layout first. When the shell itself needs building or changing, assign `app-shell-design` to cross-page hierarchy, route context, content boundaries and scroll ownership; page leads retain content ownership. Not every administration page is a dashboard: standalone order lists and settings forms do not require a metric-card workflow.

Use `ui-ux-pro-max` only when candidate coverage or required UX evidence is insufficient, for research and recommendations. A catalog's dashboard-looking marketing image does not replace dashboard methods. Dashboard and component capabilities implement the page. Establish states, filter scope, refresh behavior, keyboard support, and narrow-screen strategies before implementation.

Do not route `gpt-taste` to dashboards, internal tools, or business-operation regions. Existing capabilities may implement desired visual features; retain useful feedback, expansion, and state transitions.

**Completion evidence:** information supports role-specific decisions, metrics are meaningful, filters match content, real and sample data are distinguished, and key actions work on target devices.

## Application shells and page continuity

Use `app-shell-design` when the shared frame needs work. Agree on route metadata, heading/action slots, content width/inset and the actual scroll container before page implementation. An existing adequate frame needs no new shell workflow.

When paired with `data-list-design`, let the list own query, page, selection and result validity. Name one coordinator for the return sequence after the relevant content is ready; preserve the agreed page/local scroll positions and restore focus to a stable record or useful fallback. See the [handoff contract](design-contract.md#shell-and-page-return-ownership).

**Completion evidence:** verify a shared list → detail → edit → Back flow in the actual frame, including a record that leaves the filtered result. Separate module demos do not prove their combined restoration behavior.

## Complete data lists

For a complete order, customer, asset, or other administrative list, assign `data-list-design` as the list-region lead. Reuse the product shell and tokens. The lead decides field priority, query/results layout, required view/column controls, selection and export scope, and return from detail; the task does not require every possible feature. `component-system` owns Table and shared control implementation, while interaction and responsive modules fill demonstrated gaps. Keep one implementation owner per component.

**Completion evidence:** the page distinguishes current-page selection from all matching results, handles empty results, restricted actions and partial bulk failures, and restores the agreed query, page and position after detail navigation. Check real text contrast, keyboard focus and narrow-screen field access in a running implementation; specifications alone do not establish runtime success.

## E. Explore a design direction

Derive constraints from business goals, audience, and available material. `global-style-skill` can recommend or compare directions without generating tokens or page code. It uses its selection guide and relevant local references on demand; `ui-ux-pro-max` or available research capabilities supplement unresolved candidate or evidence gaps. Do not require both workflows when one has answered the question.

Inherit established branding and reference scope unless the user changes them. A sufficiently clear new-project brief permits a reasoned provisional choice and continued work; style selection is not a mandatory questionnaire. When a material choice cannot reasonably be inferred, present two or three concrete alternatives with their practical differences. Follow the user's explicit preference and check its fit within the requested region.

When image concepts are the requested deliverable and tools are available, select the relevant web, mobile, or brand-board entry from the external catalog. Classify these outputs as reference images, not working interfaces or adopted token systems. Specialized classics still require explicit opt-in.

When the user requests candidates only, do not record one as an approved brand. A provisional recommendation with reasons is appropriate. When asked to establish conventions, turn the adopted direction into concrete agreements and implementable tokens. Do not automatically generate an entire site.

### Style-routing distinctions

| Request | Route and stopping point |
| --- | --- |
| Build a new daily operations dashboard for frequent desktop use; choose the appearance | Let the dashboard lead establish task structure and density. If direction remains open, use relevant global-style guidance, choose a suitable provisional direction, and continue. No routine question, all-card loading, or automatic research pass |
| Give this page a soft, minimalist appearance | Apply the requested traits within its scope through the current lead/global style as needed; this does not authorize `high-end-visual-design` or `minimalist-ui` invocation |
| The product has complete tokens; change the whole product to a specified new visual direction | Allow global-style selection/migration, preserve the named token authority, and coordinate affected owners. Existing complete tokens do not cancel the explicit redesign request |
| Compare two suitable directions for this tool; do not implement yet | Use global-style recommendations and relevant references; add research only for a concrete gap. Explain the choice and stop before token edits, page code, or external creative workflows |

## Product-reference research and transfer

Route named-product comparisons and source checks directly to `design-reference-research`; global style or a page lead may also request it for a concrete evidence gap. Start with the package's metadata, read usually 1–3 relevant cases, and return decisions to the current owner. Scope and evidence quality outweigh brand familiarity. Use these scenarios when checking the route:

| Request | Route and completion evidence |
| --- | --- |
| Compare Linear and Notion for a developer-tool marketing site; advice only | Inspect their marketing cases, compare concrete surface/type/content relationships and cite sources; stop before tokens or page code |
| Build an operations dashboard inspired by Linear | Keep `dashboard-design` in charge; identify the bundled Linear case as marketing evidence. Borrow only suitable visual traits and supply business states/data behavior through the existing modules; do not claim a complete Linear workspace specification |
| Reproduce SAP's real business app from its catalog examples | Inspect the example's provenance. Illustrative SaaS surfaces are not native-product evidence; use an actual supplied or reachable product reference for faithful reproduction. If unavailable, state the gap and distinguish any proposed adaptation |
| Our theme is complete; fix mobile table overflow | Use the local responsive/page owner and existing theme. Skip case research and token regeneration unless the request separately asks for a named comparison |
| Use a named source that has only an indexed record | Locate its pinned source, inspect scope before recommending traits, and mark newly examined evidence accurately. If inaccessible, report the limit and continue allowed work with available methods; the index alone proves no design details |
| Apply an Airbnb-inspired listing pattern with long Chinese titles on narrow screens | Use its marketplace case for structure/information relationships; retain the product theme, adapt Chinese typography, and define missing loading/error/keyboard/narrow behavior. Verify those in the implementation rather than claiming the source already did |
| Turn adopted case decisions into our project's DESIGN.md | Record scope, chosen traits, provenance and supplemental decisions; link the existing token authority. Document delivery neither changes the brand without authorization nor runs Stitch automatically |

A source document or scenario walkthrough is evidence of research/routing only. Visual improvement, responsive success and working interactions require actual generated-page checks. No suitable case is a valid research result; continue with established product rules instead of forcing a brand match.

## F. Image concepts and tool-specific documents

Choose from the requested output. Website section images use `imagegen-frontend-web`; app screens/flows use `imagegen-frontend-mobile`; identity boards use `brandkit`. Keep the user's specified count and format, such as three app screens producing three images. Check an actual image-generation tool before promising image output; proposed prompts or descriptions are not generated pictures. Do not add frontend coding, project-token adoption, or a complete style workflow to an image-only request.

When the user explicitly chooses `stitch-design-taste`, distinguish its `DESIGN.md` from Stitch-generated screens and runnable HTML. Stitch MCP is optional upstream; check actual Stitch access rather than assuming absence of that one connector means no access. When the whole tool is unavailable and ordinary HTML is an accepted alternative, let the page implementer complete HTML; do not pause solely to obtain the optional connector or claim Stitch ran. If only document guidance is used, identify that scope.

## Mixed scenarios and local fixes

Marketing and application regions may share brand colors, icons, and base components while differing in typography, density, and motion. Assign a lead and change scope to each region. Marketing effects must not become defaults in business regions through shared components.

Use responsive capability for mobile table overflow; interaction capability for dialog focus and submission feedback; component capability for consistent button variants. If the matching skill is absent, solve the issue directly under project conventions rather than substituting an unrelated full-page workflow.

For missing capabilities, version conflicts, and new modules, read [discovery and adaptation](skill-adapters.md).

Reuse loaded parent and shared rules within the task. For example, adding a deletion Modal to an existing themed table needs the overlay and relevant submission/recovery guidance, not all interaction siblings, new tokens, a new table design and a second responsive pass. If a new requirement introduces a genuine gap, add only that contribution and return it to the existing implementation owner.
