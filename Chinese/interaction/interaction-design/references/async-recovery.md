# 异步反馈与恢复

处理请求、自动保存、远程开关、筛选、撤销或批量操作时读取。以下是实现建议，依目标系统实际接口调整。

## 最小完整生命周期

`idle/edited → pending → confirmed | recoverable-error | outcome-unknown`。

本地校验失败先返回填写阶段，不发送无效请求。只有业务返回并确认成功才进入 confirmed；网络超时或连接断开可能是 outcome-unknown，不能一律当成服务端未执行。

| 触发条件 | 状态变化 | 用户反馈 | 退出或恢复 |
| --- | --- | --- | --- |
| 有效提交 | edited → pending | 原位置显示进行中，保留当前内容与操作上下文 | 防重复守卫；允许与该动作无关的操作继续 |
| 成功确认 | pending → confirmed | 说明什么已保存；短暂成功动效可选 | 更新已保存基准；按任务停留、关闭或跳转 |
| 可确认失败 | pending → recoverable-error | 明确原因、受影响对象与可用下一步 | 保留输入、选择和失败对象，允许修正/重试 |
| 超时、断线且结果不确定 | pending → outcome-unknown | 说明暂未确认结果，避免宣告“已撤销” | 查询状态/刷新对账；仅在可安全重复时重试 |
| 用户离开/取消等待 | waiting → detached/cancel-requested | 区分停止等待与取消业务动作 | 请求取消成功需要服务端依据；稍后结果按任务可追踪 |

前端按钮禁用只解决部分重复输入；处理函数也需检查执行中状态。涉及付款、创建、删除或批处理时依据后端支持使用幂等标识/任务标识。原地重试不能无意创建第二笔业务。不要用自动重试无限放大失败。

## 让等待与结果可理解

- 短请求不人为延迟以播放加载动画；较长任务给真实阶段或可用的进度。没有可测总量时用不确定进度，不编造百分比。
- 首次加载可用与真实区域相近的骨架。已有数据刷新时通常保留旧内容并明确“正在更新”，避免每次输入清空页面。
- 轻量成功可用成功标记、Toast 或状态条；所有错误都不使用 Toast。字段错误就近内联，持续的同步/网络失败用 Alert，并与受影响区域关联。具体承载方式遵循 [浮层选型](../sub-skills/floating-components/SKILL.md)，不能靠延长错误 Toast 的时间规避限制。
- 重复保存、自动保存等低干扰反馈保持稳定位置；不要每次自动把焦点拉走。

## 竞态与草稿

| 问题 | 需要保持的事实 | 可行处理 |
| --- | --- | --- |
| 输入 A 后又输入 B，A 的响应更晚回来 | 屏幕结果对应当前已应用查询 | 取消可取消请求，并用请求标识/当前查询检查拒绝旧响应；取消本身不足以证明旧响应不会到达 |
| 保存期间又编辑 | 成功只确认已提交版本 | 保存请求带提交快照/版本，后续修改仍标未保存；不拿旧返回值覆盖新草稿 |
| 编辑中其他人更新 | 双方内容不能静默覆盖 | 依据版本冲突提示重新载入、比较或再次保存；行为服从实际接口 |
| 组件卸载或切换实体 | 前一个实体的结果不写入新实体 | 绑定实体键和请求身份，清理监听/动画/计时器；必要时保留任务结果入口 |

输入去抖只合并查询，不决定服务端顺序。去抖时长采用项目约定或局部可调值；为用户主动提交提供即时执行路径，考虑输入法组合事件。

## 乐观更新、撤销与局部失败

适合乐观更新的条件：能可靠还原、冲突可解释、错误代价可接受。记录操作前值与对象身份，失败回滚仅撤回该操作，不能把之后成功的修改一并覆盖。高影响或结果不确定的操作优先等待确认。

撤销需明确是“延迟发送前取消”还是“已提交后执行反向操作”。提示期限依据实际可撤销窗口，过期移除动作或解释不可撤销；不能只倒放动画。倒计时结束也不能自行证明服务端成功。

批量操作逐项记录成功、失败、尚未处理与结果未知。不要只显示整体失败然后重跑已成功项；重试作用于可安全重试的集合。删除当前行后焦点放到合理相邻行或表格入口，且告知实际结果。

## 代表性推演

编辑抽屉输入后保存失败：打开并定位 → 提交有效草稿 → 显示保存中且防重复 → 模拟返回失败 → 抽屉保留、输入未丢失、错误可读 → 修正或重试 → 成功确认 → 按任务关闭并返回焦点。检查过程中再覆盖“请求未结束就继续编辑”和“超时实际已提交”的分支，不能用固定延时的勾选动画替代它们。
