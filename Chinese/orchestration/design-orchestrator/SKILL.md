# 设计调度入口

识别任务，选择足够完成工作的最小模块组合，归并共享决定并完成所需交付。详细方法由子模块负责，不把正文合并进入口，也不以调度方案替代用户要求的实现。

## 确定任务

先判断交付物：建议、审计、设计图、Token 或可运行代码；再看改动范围、参考依据、现有主题与组件、页面用途和可用工具。局部问题优先于页面大类。复用已有上下文，用户明确要求优先；仅为相关缺口读取项目规范或 [共用约定](references/foundations.md)。

## 按职责选择

这是职责表，不是依次执行的流水线。选择合适主力，只有具体缺口或用户要求独立复核时才增加辅助。

| 需求／触发条件 | 主责及产物 | 边界／辅助条件 |
| --- | --- | --- |
| 选择／比较视觉方向，或新增／变更／检查共享视觉值 | `global-style-skill`：推荐方向，按需生成或校验 Token | 主题或主力已有适用方向／值时复用；明确改风格时，即使 Token 完整也可能需要选型 |
| 业务总览、分析、监控、工作台 | `dashboard-design`：内容层级、指标、图表与必要状态 | 负责看板区域，复用其中已满足要求的组件、交互与窄屏行为 |
| 完整后台数据列表页 | `data-list-design`：信息优先级、查询与结果、选择、批量任务、导出范围及详情返回连续性 | 沿用产品框架和 Token；Table／公共控件由 `component-system` 提供；交互、响应式只补缺口 |
| 应用外壳、跨页导航或框架一致性 | `app-shell-design`：信息架构、标题区、内容边界与滚动归属 | 已有框架足够时复用；页面主力负责内容；导航、组件、响应式只补缺口 |
| 公共组件、接口、变体或缺失基础组件 | `component-system`：可复用实现 | 页面编排及业务语义由页面执行者负责；行为有缺口才加专家 |
| 按钮、表单、导航、浮层行为 | `button-interaction`、`form-interaction`、`navigation-interaction`、`floating-components`；`interaction-design` 协调共享行为 | 选相关子入口，共享父规则读一次；跨组件或异步行为按需读父入口与相关方法，不全读兄弟模块 |
| 重排、触屏、导航收纳或溢出 | `responsive-design`：局部适配 | 保留组件类型、交互约定和视觉系统 |
| 相容的官网或作品集 | `design-taste-frontend`：页面设计与实现 | 先核对实际默认规则和依赖；旧站／局部修复保持范围，完整流程冲突时选用部分指导或更换主力 |
| 补充风格、字体或 UX 依据 | `ui-ux-pro-max`：研究与建议 | 只补尚缺的候选／依据，不自动增加研究步骤，不接管页面代码或替换已采用 Token |
| 具名产品参考、来源核查或具体设计案例比较 | `design-reference-research`：限定范围的案例、证据和可迁移模式 | 先读元数据再读相关案例；区分营销、产品界面和演示示例；建议交回原负责人，不自动替换主题或重复研究 |
| 忠实实现已有图片 | 能读图的页面执行者：按目标实现代码 | 保留原图依据，不重新生图；必要提取／校验 Token 时才加全局风格 |
| 只生成设计图 | `imagegen-frontend-web`：网页区块；`imagegen-frontend-mobile`：应用屏幕／流程；`brandkit`：品牌板 | 需要可用生图工具，保留要求的数量和格式；图片不等于代码或已采用 Token |
| 先生成设计图再实现 | `image-to-code`：图像先行创建及代码 | 需要生图与编码能力，不替代已有图片还原 |
| 明确选用特定创意风格 | `gpt-taste`：创意营销；`high-end-visual-design`：柔和精致；`minimalist-ui`：克制；`industrial-brutalist-ui`：工业机械 | 遵守上游明确选用策略，选合适主力，不叠加完整风格流程；`gpt-taste` 不用于业务区域 |
| 明确选用 Stitch 流程 | `stitch-design-taste`：面向 Stitch 的 `DESIGN.md` | 区分设计文档、生成屏幕和前端代码，核对实际工具访问 |
| 明确要求历史兼容 | `redesign-existing-projects`、`design-taste-frontend-v1`、`design-taste-frontend-v2-experimental` | 使用明确选定的固定版本，不因当前 Skill 缺失而自动回退 |

设置表单等尚无可用的专门页面 Skill 时，由当前执行者负责页面编排与业务流程；组件、交互、响应式补具体缺口，不把所有后台页面套成 Dashboard。

每区域一个主力，每组件一个代码负责人。混合官网／业务应用按区域分工，共享权威主题。目录说明与调用标志描述的是上游能力，不覆盖本表分工；泛泛的审美偏好不触发需明确选用的 Classics。需求、工具或实际缺口变化时再调整路线，按分工完成工作，不循环交接。

## 发现并复用已读规则

只选一个语言版本。有 MCP 时先看 `catalog_skills` 元数据，再用 `load_skill` 读选中入口。别名归一：`taste-skill` 与 `design-taste-frontend` 是同一项。不同安装副本同名时选一个相容的明确 id，不混合副本或语言版本。

同一任务中按解析后的文件身份与 revision 复用已读入口和资源。父入口回链、别名、第二个辅助角色不意味着重读相同内容或重跑流程。内容变化、上下文已无所需规则、或新范围需要未读指导时再读。MCP 无会话状态，不替执行者管理这份工作记忆。

`read_skill_file` 读取选中入口及相关资源中明确提及的必要文件，既包括 Markdown 链接也包括行内文件名。`linked_resources` 只是便利索引，不是完整依赖清单；按需继续分页，revision 变化时重读。不遍历全部素材或预读未选中的正文。

产品案例研究先发现 `design-reference-research`，再使用它的小索引，通常选择 1–3 个案例。`catalog_skills` 搜索 Skill 元数据，不搜索案例正文；现有读取器不执行语义搜索。已建立索引不等于已审查案例。已有主题的局部修复跳过研究，除非请求中包含具名参考比较或证据缺口。

无 MCP 时从可用技能、用户入口或声明目录发现相同模块。核对所选流程的真实依赖；缺普通能力时直接完成并说明回退。用户必须采用特定方法且无可接受替代时，只获取缺失依赖，同时推进独立工作。不自动安装同名包，不声称不可用工具已运行。

冲突／新接入读 [适配约定](references/skill-adapters.md)，复杂组合读 [场景细则](references/scenarios.md)，来源／版本选择读 [外源清单](references/external-catalog.md)；普通任务跳过无关参考。

## 归并与交付

新主题复用主力已选的适用方向，或通过全局风格的按需参考库选型。信息充分时直接作出有依据的暂定选择，只询问无法推断的重大取舍；普通局部修复无需选风格或问卷。采用相容主力生成的值，或由全局风格补齐缺失值，再校验单一权威 Token 源，不安排两个模块各造一套。已有主题及忠实参考在指定范围内继续有效，除非用户明确变更。纯咨询停在建议，不应用主题或编写页面代码。

简述交付物／区域、主辅职责、Token／组件来源、具体缺口与验收范围。辅助提出变更，由负责人整合；跨区域或聊天需要记录时读 [交接约定](references/design-contract.md)。产品 Token 留在产品项目。完成任务后报告实际使用的模块、成果与检查，不声称执行了未做的工作。
