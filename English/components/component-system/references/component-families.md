# Component anatomy and family decisions

Read only the families used in the task. The structures below guide composition; use equivalent parts already provided by the installed library.

| Family | Useful anatomy | Selection and interface decisions | State and reuse checks |
| --- | --- | --- | --- |
| Button / icon action / split action | Action surface, label, optional leading/trailing icon, pending indicator; split action has a separate menu trigger | Button for actions, link for navigation. Icon-only needs a name. Split only when a meaningful default action has related alternatives. Preserve native submit behavior | Pending is driven by work, not animation; duplicate prevention; focus and label remain clear; menu trigger independently named |
| Input / Field / textarea | Label, control, optional prefix/suffix, help, error; optional count or clear action | Field supplies relationships and layout; control integrates with existing form state. Separate value from display formatting. Clear/visibility controls are independent actions | Preserve input after failure; associate label/help/error; distinguish readonly/disabled/invalid; long labels and error messages can grow |
| Select / combobox / option group | Label, trigger or editable input, current value, indicator, popup, options; optional clear, description and search/loading area | Small simple lists may use native Select. Search needs justify combobox; several visible alternatives may fit radio buttons. Single versus multiple, local versus remote search, stable keys versus labels, explicit empty value | Keyboard selection/escape; focus versus selection; duplicate labels; clear semantics; loading/error/no match distinct; popup clipping and focus return |
| Checkbox / radio / switch | Control, visible label, optional description; checkbox may have mixed state | Checkbox expresses independent choices, radio one of a set, switch an immediate setting when the product uses that pattern. Do not choose only by shape | Correct checked/mixed/disabled contract; group label; async change and failure recovery match actual persistence |
| Tag / badge / chip | Text and optional status marker, icon, count or removal action | Distinguish passive status, selectable filter and removable value. A passive tag need not be focusable; a selectable chip needs control semantics | Text accompanies color; selected/removal behavior explicit; remove control named; wrapping/overflow and nearby targets remain usable |
| Card / surface | Optional media, heading/description, body, metadata, actions/footer | Add a boundary for a real content group. Compose regions instead of many page-specific props. A surface treatment need not create a new component. Clickable card has a clear main action | Avoid nested links/buttons and ambiguous click areas; secondary actions independent; long content; surface foreground pairs; consistent region padding |
| Table / data region | Caption/name, header, rows/cells, optional selection, toolbar, pagination, empty/loading/error region | Choose a native table or established table component for data; use a grid only when its richer keyboard model is needed and implemented. Keep columns, row keys, sorting/filtering/paging and selection ownership explicit | Stable keys under sorting/paging; zero versus missing value; selected keys across pages defined; sort state announced; cell buttons usable; narrow overflow keeps meaning |
| Navigation / tabs / pagination | Landmarks/groups, item label, optional icon/count, current/selected marker, overflow controls | Links navigate; tabs switch related panels; menus present actions. Page lead defines destinations and hierarchy; component implements their contract. Do not assign menu roles to ordinary site navigation | Active/current differs from focus; keyboard and panel association; long labels; collapse/overflow maintains access; no shared global active index across independent instances |
| Modal / Drawer / Popconfirm | Existing overlay shell, title/description, body, actions, close/return path; optional trigger | Reuse the existing overlay capability and its selection rules. Component owner integrates content slots, open state, theme and focus access; page owns business work | Modal background/focus contract; portal theme and layering; nested overlays; draft/pending/close rules; failure remains readable; focus returns to a sensible place |
| Tooltip / Toast / Alert | Associated explanation or result, optional icon and appropriate action | Follow the project's overlay/message distinctions. Required instructions remain visible/associated; persistent errors need persistent UI | Tooltip is not an interactive menu; success follows real outcome; no timer hides unresolved errors; announcements and dismissal do not steal focus |

## Composition choices that matter

- Keep the Field label and error association even when replacing its inner control. An attractive input with no form binding is not a complete reusable field.
- For editable remote selection, separate typed query, committed selection and fetched options. Cancel or ignore stale requests through the existing data layer; keep selected identity when labels repeat or options reload.
- A selected card needs a real selectable control or equivalent correct semantics. A shadow and a `selected` class alone do not implement selection. Add a checkbox/radio or a suitable link/button without wrapping interactive descendants inside another control.
- Table density changes the row and embedded controls as one system. Pagination, server filtering, row selection retention and bulk actions must agree on which data set is being operated on.
- Keep visual affordances and behavior matched: a drag handle needs a non-pointer path for the task; a hover reveal must not hide the only action from keyboard/touch use. For complex patterns, reuse proven primitives rather than recreating focus and selection mechanics from a screenshot.

The implementation minimum derives from the project foundations. Useful semantic references, to consult when building those behaviors, are [WAI Button](https://www.w3.org/WAI/ARIA/apg/patterns/button/), [WAI Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), and [WAI Table](https://www.w3.org/WAI/ARIA/apg/patterns/table/). These describe distinct patterns; they are not certification of any library or finished product. Overlay conventions are summarized in [foundations](foundations.md).
