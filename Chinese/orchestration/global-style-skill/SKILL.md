# 全局风格与设计 Token

处理当前产品的视觉方向、设计 token 及其使用一致性。由主控调用时接收本次范围和设计依据，返回可用结果，由主控归并输出；独立使用时按同样规则完成任务。在当前范围内提出视觉处理建议，页面负责人决定构成与业务语义。不实现页面或组件，不加载其他业务 skills。

## 接收依据

从需求与目标项目读取本次任务类型、现有主题来源、已定品牌、参考用途、允许修改范围和输出格式。目标项目提供的设计规范优先；本系列的共用规范与模块记录仅在目标项目存在时读取。没有这些文件也可独立运行，不寻找制作本 skill 的原目录。

先区分方向建议、生成、局部扩展、迁移或只校验。已有完整 token 且用户只修交互时，返回其来源及“无需变更”；不为每个请求重建主题。即使 token 完整，用户要求的风格比较或视觉变更仍属于本模块。只咨询时返回建议，不写 token 或页面代码。缺少普通细节时提出有依据的暂定值，注明候选状态；仅对会改变结果且无法推断的关键冲突提问。

主题已确定，不代表受影响页面与组件已经正确使用。本模块可只在交付阶段参与校验，无需重新选择方向或生成数值。实现者已完成且充分的校验应直接复用。

## 决定视觉依据

- 新项目先依据受众、页面用途和参考确定方向，再给具体值。没有参考时可给明确标为暂定的起点，不能把自行选择写成用户偏好。
- 忠实还原时以指定设计稿为视觉依据；融入既有产品时，将参考中的角色映射到现有主题。两者的强制要求冲突时先解决取舍，不在交付前偷偷替换颜色或形状。
- 源设计或代码可核对的数值直接采用；截图中无法精确测量的颜色、字体和尺寸标为估计。仅探索候选时不覆盖项目当前主题。

## 按需选择方向

存在开放的风格选择或比较任务时，读取[选型规则](references/style-selection.md)。通过[风格索引](references/styles/index.md)定位相关候选，再只读对应卡片。它们是可组合的参考属性，并非40套必选模板或新增 skills。已有视觉设定与局部修复跳过参考库，除非用户要求重新考虑。适配当前任务的负责人已经确定方向时复用其结果，不再进行第二轮选型。

任务明确或用户交由你决定时，选择并简短解释一个暂定方向。只有明显不同的方向都合理、且无法推断用户偏好时，才提供2–3个具体选项让用户决定；等待期间暂停依赖该选择的视觉变更，继续独立工作。明确参考与当前指令优先。选型规则说明交接、组合边界、证据限制和可选研究，不强制依赖其他 skills。

明确要求案例分析／比较或来源核实，或具体案例证据不足时，使用当前可用的 `design-reference-research`，遵循选型指南的证据规则。具体视觉借鉴先检查所给材料或复用充分的已查证据，除非用户明确要求研究，否则只研究剩余来源缺口。名称仅用于表达氛围且方向依据充分时，无需案例研究；记录所需气质，不声称观察过产品细节。研究元数据与选定案例补充同一次决定，不另开主题流程。区分来源观察、建议和合成示例，将采用特征映射到已有 Token 源。普通局部修复跳过研究。该模块缺失时直接检查用户所给证据并说明剩余缺口，本 Skill 仍可独立使用。

## 生成与归并

先定位可编辑的权威来源与生成关系。复用现有 CSS 变量、主题对象或组件库配置；生成结果由上游配置产生时修改上游，避免同时维护两份可独立变化的值。

按当前用途补齐必要内容：

| 类别 | 要表达的用途 |
| --- | --- |
| 颜色 | 主色、背景与表面、文字层级、边框、交互状态；业务状态与图表色按需补充 |
| 字体 | 字体及回退、字号层级、字重、行高，必要时数字样式 |
| 间距 | 有用途的间距尺度、容器边距与组件内边距 |
| 形状 | 圆角尺度、描边，确有需要时增加阴影与层级 |

输出实际可使用的值、单位、语义名称与引用关系，不只写“高级灰”“适中圆角”。沿用项目命名和格式，检查重复名、无效值、缺失引用和循环引用。颜色与字体选择要适配实际背景、语言与可用资源，不声称未加载的字体已生效。

局部差异使用命名明确的组件或区域变体。官网大标题与后台紧凑表格可以不同；同名全局值不能被各页面悄悄重定义。新增或修改共享值时列出用途、旧值、新值、理由与受影响范围；主控协调其他区域，本模块只修改本次获准范围。

## 校验实际产物

以当前采用的设计决定和权威来源对照指定文件或界面，检查实际色值、字体、间距、圆角是否正确引用，是否出现意外覆盖、缺失变体或无效引用。修改局部颜色前先分类：共享语义角色的冲突需要协调，刻意采用的区域变体需要明确作用域，插画或装饰常量可以保留在局部。直接写入的数值，包括固定图标尺寸，不自动判为错误。

实现中新增多个区域或修改共享主题值时，除校验来源外，还应验证有代表性的受影响页面与组件：

- 选择能覆盖相关共享值不同用途的页面或共享组件。检查相关可见状态，如焦点、选中、错误或禁用，不只看默认状态。
- 检查实际前景与背景组合及主题继承。存在且受到影响时，包含图片或透明背景，以及通过 Portal 或在主题容器外渲染的浮层。
- 明确由谁整合发现，可以由同一实现者负责。复用仍然有效的证据，只补未覆盖或已变化的用途；无需另设审阅者、创建新主题，或遍历全站所有状态。
- 在现有项目记录或要求的输出中，写明检查过的页面与组件、状态与条件、结果或修复位置，以及未验证范围。只检查源文件不能证明渲染后的使用情况。

只要求校验时，返回可定位的问题、证据和修正建议；要求修正时落实范围内的主题改动。当环境具备 Python 3.11+ 时，可对 CSS 或 JSON Token 文件运行 [check_tokens.py](scripts/check_tokens.py)（`python scripts/check_tokens.py <file> [--pair --fg:--bg]`），确定性检查同作用域重复定义、未定义的 `var()` 引用、循环引用及不透明 hex/rgb 颜色对的 WCAG 对比度；静态脚本校验用于补充而不是替代渲染后的页面检查。对比不足等视觉问题需依据实际组合检查，不能只凭变量名判断。用户明确采用的新方向作为变更处理，不机械退回旧规范。

## 输出给主控或用户

按要求交付方向建议、项目原格式的 token 文件或修改结果。风格决定需说明具体特征、区域边界、依据及采用或暂定状态，以及尚未解决的选择；轻量交接方式见选型规则。简短记录任务类型、权威来源位置、变更与作用域、受影响区域、校验发现和实际验证范围。位置使用目标项目相对路径。只做候选方案时输出候选及建议，不写成已应用结果。

主控可直接把结果传给页面与组件模块，不需要重新生成一套值。记录应能在后续窗口接续，但不要把当前产品的品牌写回技能库。实际运行和渲染未检查时明确说明，不把文件校验当作页面验证。

依据：《界面共用设计规范》0.2 与本系列分层调度约定。方法已包含在本文件中，无外部项目或其他 skill 的必需依赖。
