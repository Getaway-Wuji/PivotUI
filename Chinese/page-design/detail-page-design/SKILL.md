# 实体详情页设计

将单条业务记录组织为清晰可读、可判断、可安全操作的核查界面。负责详情区域结构、信息分组、操作入口安排、异常/缺失状态与返回连续性；沿用产品既有应用框架、共享组件与权威 Token 来源。

## 建立工作约定

从需求与目标项目中明确：实体类型与稳定 ID、用户进入详情页的首要判断或审批目标、关键状态与异常提示、信息分组维度、关联集合或变更历史、可执行操作与权限边界，以及来源路径（列表跳转、直达深链或搜索结果）。常规细节基于合理假设直接推进，仅在业务规则缺失且影响结构或权限时提问。

## 组织详情界面

1. **首屏先明身份与状态**：在框架内容区顶部清晰呈现记录标题、稳定编号、当前生命周期状态及主/次操作入口。破坏性操作与常规编辑在视觉与位置上明确隔离。
2. **按决策相关性分组，不平铺字段墙**：按使用频次与语义拆分模块（核心摘要、业务明细、归属与时间、关联记录、操作日志）。编号、金额与日期使用等宽数字对齐；明确区分零值、空值（`—`）、脱敏值与未加载状态。
3. **阅读态与编辑态边界清晰**：保持只读核查的整洁度；较复杂的多字段编辑交由 `form-workflow-design` 或约定的编辑路由/抽屉处理（浮层选型遵循 `floating-components`，不把全屏编辑强塞进 Drawer）。
4. **完整覆盖非理想状态**：处理加载态、记录不存在或已删除（404）、无权限（403）、并发过期/刷新冲突，以及次级关联模块加载失败时局部降级而不影响主记录展示。
5. **保持返回连续性**：从详情或编辑返回列表时，保留来源历史条目的筛选条件、页码与有效定位（由 `data-list-design` 与 `app-shell-design` 约定同一返回协调者）；直达深链时提供可靠的父列表返回入口。

## 整合与验证

`app-shell-design` 负责持续导航、面包屑与外层滚动容器，详情页不得假定 `window` 是滚动容器。`component-system` 负责共享描述列表、Tabs、标签与表格控件；`interaction-design` 与 `responsive-design` 按需补齐未覆盖的交互与窄屏重排。

交付所请求的设计规格或可运行页面，说明采用的 Token/组件来源、覆盖的异常状态（缺失、无权限、过期、深链）、返回行为以及实际完成的运行或静态检查。包范围见[包说明](PACKAGE.md)。
