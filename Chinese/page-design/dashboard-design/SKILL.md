# Dashboard Design

把业务问题转化为能阅读、能判断、能行动的仪表盘。先选任务结构，再选视觉语言，最后添加有用途的交互。用户要求复现指定参考时，以该参考为起点，保留其明确要求。

## 先读取项目约束

- 先检查目标项目已提供的设计规范与组件约定。项目采用本系列目录约定时，按项目根目录解析 `design-system/FOUNDATIONS.md` 和 `design-system/modules/dashboard.md`，仅在文件存在时读取；这些可选文件不是使用本 skill 的前提。
- 目标项目没有设计规范时，读随包的 [共用设计约定](references/foundations.md)，摘编自《界面共用设计规范》**0.2，2026-11-14**。目标项目规范优先；摘编只补充未规定的方法。
- 本 skill 的 Markdown 资源链接均相对于所在文件解析；方法已整理成文字规则，无需读取制作时的原图或研究笔记。
- 当前参考库没有确定目标产品的品牌色、字体、主题或圆角。下面的风格和数值都是可选方案，不能写成用户既定偏好。采用的值记录在目标产品中；只有用户明确修改本系列通用方法时才更新系列共用规范。
- 负责 Dashboard 的内容区域、指标层级、图表、概览中的摘要列表和必要交互。沿用已有页面框架；仅在用户要求或无现成框架时选导航变体，不顺带重做全站表单和列表。

## 与主控接续

本 skill 可以独立使用，也可以由 `design-orchestrator` 分配任务。已收到主控的工作约定时，承接其区域、角色、参考用途、token 权威来源、现有组件、目标设备、可改范围和验收依据；已明确的决定直接沿用，不重复索取。用户的新明确要求优先，发生变化时同步约定。

- **按分工工作**：作为主力时完成分配的 Dashboard 内容；作为参考还原的辅助时，只检查约定的数据语义与状态，不另选构图或接管整页。
- **统一公共样式**：把配方映射到约定的 token 和组件。新增公共值或共享组件变更交由主控职责统一归并，局部差异使用有名称的变体；不另建一套可独立漂移的主题。主控与实现者可以是同一执行者，无需额外审批环节。
- **按需补足能力**：复用本 skill 已有的交互和窄屏规则。组件、交互或响应式 skill 尚不可用时，由当前执行者按约定补足并如实记录，不宣称调用了缺失能力。本系列不使用 `gpt-taste` 处理业务区域；`ui-ux-pro-max` 若可用，仅提供研究与建议。
- **交回可核对结果**：说明完成区域、产物与修改文件、实际采用的 token/组件、提出或归并的公共变化，以及已验证和未验证的行为。无需把全部研究资料重新交给主控；已有项目记录即可承载交接。

用户直接调用本 skill 时，继续完成仪表盘任务。若项目已配置主控，且此次需要新建应用框架、调整全局样式或协调其他区域，先按当前环境的可用目录定位并读取主控入口与所需约定；本系列的 `design-system/ORCHESTRATION.md` 仅在目标项目存在时读取。已有明确分工时不反复回到主控重新路由，独立分发也不依赖主控包存在。

## 从需求做出选择

先从现有需求、数据和项目中获得这些信息，缺失且会改变方案的内容才问用户；普通空缺以明确标注的假设继续：

| 要知道什么 | 会改变什么 |
| --- | --- |
| 谁使用，进来最想判断／完成什么 | 页面主线、第一屏优先级 |
| 关键指标、对象、单位、口径、时间范围 | KPI 和图表是否成立 |
| 查看频率、数据延迟、异常处置要求 | 概览、探索还是监控 |
| 数据量、分组维度、比较对象 | 密度、图表、摘要与明细边界 |
| 品牌／现有组件／主题、设备和交付形式 | 风格、响应式与实现范围 |

写出一句内部设计命题：**“让［角色］在［场景］判断［问题］，据此［行动］。”** 无实际行动时可以是理解、汇报或比较，不强加操作按钮。

### 1. 先选一个主结构

根据 [selection-guide.md](references/selection-guide.md) 选择主结构：

| 编号 | 页面任务 | 第一屏优先 |
| --- | --- | --- |
| A | 经营概览 | 结果、目标差距、主要变化和原因入口 |
| B | 分析诊断 | 筛选上下文、主分析图、分组比较与下钻 |
| C | 实时监控与处置 | 异常、影响范围、时效、处理入口 |
| D | 任务与团队工作台 | 我的待办、截止风险、进度、资源分配 |
| E | 账户与资源概览 | 当前余额／容量／状态、流入流出、近期事件 |
| F | 内容与资源发现 | 内容预览、分类、搜索与最近访问 |
| G | 专题叙事与成果报告 | 有证据的核心发现、趋势、解释与出处 |

确定一个清楚的主任务，再按实际需要安排解释区与执行区。多个任务争夺首屏时，按角色、处理时限和访问目的判断，必要时分角色视图或下钻；不规定辅区数量。行业只是线索，同一电商系统的老板、运营、仓管应有不同主结构。

### 2. 沿用或选择视觉语言

已有完整主题且要求保留，或指定设计是忠实还原的视觉依据时，记录该来源并沿用约定的视觉。不必选择配方或读取 `visual-recipes.md`，除非具体视觉缺口或用户要求的修改需要它；无需 P 编号。作为还原辅助时继续遵守已分配范围。

需要选择视觉方向时，先从 [visual-recipes.md](references/visual-recipes.md) 的速查表选择候选，再只读匹配的具体条目，保留其主次、留白和表面关系。

现有主题优先；无主题且需求普通时，从浅色、清晰边界、适中密度起步，不默认玻璃、荧光、全黑或彩虹卡片。用户明确点名的风格先满足，再处理可读性。

### 3. 依据问题安排内容

读 [data-and-layout.md](references/data-and-layout.md)。把每块内容写成“问题 → 数据 → 表达 → 后续动作”。主要内容回答主问题，辅助区解释或承接执行；任务队列和内容卡片也可成为主区，不强制放主图。数据不支持的可选分析应省略或换表达；用户需要但尚未接入的核心模块保留结构并说明缺失状态。概念设计可以用明确标注、数值关系自洽的演示数据，不将其写成真实结果。

在实现前形成简短决策记录：角色与任务、沿用的主题／参考来源或所选视觉方向及理由、A–G 主结构、首屏顺序、主要表达、交互、展示载体和数据状态。只有实际选择了配方才记录 P01–P11 编号。类别是帮助判断的配方，不要求所有任务严格落入一个编号；用户有明确布局时优先满足。用户只要代码时压缩到几句并继续完成实现，不额外要求批准这份记录。

### 4. 有需要才加载导航和动效

读 [interaction-patterns.md](references/interaction-patterns.md) 的相关条目。用展开、筛选、联动或命令面板解决实际操作问题。重排仅在用户需要个性化时引入。悬浮翻转、光跟随和一键聚合属于特定风格的可选效果。

参考截图只能证明静态样式；图中提示词描述的行为是“设计要求”，不能声称已观察到实现。补充的键盘、触屏、减少动态效果和错误恢复方案须作为设计补充。

## 按需读取资料

直接按上文路由读取任务所需的规则，无需先遍历来源。希望了解某种方法从哪些案例提炼时，再读 [来源与方法摘要](references/reference-index.md)。其中 S/V 编号仅用于说明来源，不代表需要打开外部文件。

用户另行提供设计图时，区分要复现的特征和业务示例。不要把海报背景、编号、水印、展示角度带入产品，也不默认保留图中的品牌、AI 助手或推广内容。要求精确复现而未提供目标图时，再索取该图；普通设计任务按现有规则继续。

## 交付与检验

按用户请求交付设计说明、AI 提示词、界面实现或已有页面修改；可用 [brief-and-prompt.md](references/brief-and-prompt.md) 组织交付。需要实现时完成可用页面与核心交互，不停在方案文字。

- 信息：第一眼能理解主问题；数据有口径、周期、单位和适用的比较基准；状态与涨跌方向不混淆；核心缺数不会被悄悄删掉。
- 视觉：一个主焦点、可解释的对齐、稳定的系列色；长标题、多位数、中文和密集列表可读。
- 操作：筛选作用范围明确，选择状态与实际内容一致；有下钻返回路径；核心信息不依赖悬停、翻转或拖拽。
- 数据状态：零、缺失、加载、空筛选、错误、部分更新和过期有区别；示例数据与真实接入状态如实说明。
- 不同设备：窄屏按任务优先级重排，保留关键告警与筛选；图表与表格有可读替代，触屏可完成关键动作。
- 实现才做渲染检查：桌面和目标窄屏、主要筛选／下钻、键盘与减少动态效果。仅输出规范时检查内容、引用和可执行性，不声称已验证界面运行。
- 目标项目已有模块记录约定时，按其约定记录来源、局部选择、实际成果和验证范围；本系列使用项目根目录下的 `design-system/modules/dashboard.md`。其他项目在交付说明中保留必要决策即可，不额外创建模块管理目录。
