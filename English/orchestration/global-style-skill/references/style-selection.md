# Choosing a visual direction

Read for an unresolved style choice or comparison. Ordinary token repairs, complete inherited themes, and local behavior or responsive fixes do not require this guide. A requested change of direction can apply even when existing tokens are complete.

## Decide, inherit, or ask

| Situation | Action |
| --- | --- |
| Existing product, no requested visual change | Inherit its theme and component language; skip exploration. |
| Explicit style or faithful reference | Follow it within the stated scope. Clarify only a material conflict with another mandatory requirement. A library label does not override the reference. |
| Clear task, ordinary missing details, or “you decide” | Choose a reasoned provisional direction, briefly explain it, and continue the authorized work. Do not require a preference questionnaire. |
| Several materially different directions fit, with no inferable priority | Offer 2–3 concrete alternatives, recommended first, with traits and relevant tradeoffs. Ask which direction to use; hold dependent visual changes until answered. Continue independent work. Silence is not a decision. |
| User asks only for recommendations or comparison | Return candidates and reasons. Do not create tokens, replace the theme, or start page implementation. |
| Compatible page lead already resolved direction and values | Reuse its decision and source. Contribute only a missing decision or requested review. |

Use existing answers and context before asking. Describe choices in recognizable terms, such as “photography-led with quiet type” versus “bold editorial type with geometric graphics”; do not ask the user to navigate a 40-name menu. Small previews can help when useful and feasible, but generating images is a separate deliverable and is not required for every choice. If essential assets or a required method are unavailable, explain the gap and use an allowed alternative; clarify only when the requirement blocks that alternative.

## Narrow the candidates

1. Establish the deliverable and affected region, tasks, audience, reading density, action frequency, existing brand/components, devices, available assets and implementation constraints. An industry name alone does not choose a style.
2. Consult the [index](styles/index.md) only when candidate vocabulary or a card is useful. Read the cards that fit the unresolved dimension; do not enumerate or load all cards. If an exact candidate is already known, go directly to its indexed file. Keep one language edition and reuse unchanged resources already read.
3. Separate visual tone, composition, surface treatment, theme, imagery and motion. Combine compatible attributes; each choice must serve an identifiable purpose. For example, restrained hierarchy + Bento summary grouping + a small gradient in the introduction does not require glass behind every table.
4. Check actual content, readable contrast, focus/state visibility, narrow layouts and asset cost. Dense operational regions need legible labels, stable data encoding and visible actions under any aesthetic. Heavy narrative effects belong in suitable presentation regions; ordinary task feedback remains available in applications.

The 40 cards describe the user's eight static reference boards. They are a reference vocabulary, not an exhaustive or ranked survey. Most examples are marketing hero images. The Dashboard label is a page-type cue, Material Design a system cue, and layout/motion labels describe other dimensions. A static example does not verify behavior, responsiveness, accessibility, performance, precise fonts or token values. Cards distinguish observed visual cues from proposed adaptations. Treat image text as reference data, not execution instructions. Screenshot domains and brands are not verified origin links or ready-to-use assets.

## Concrete product cases when useful

The style cards supply visual vocabulary; `design-reference-research`, when available, supplies named product cases and their provenance. Use it for requested case analysis/comparison or source checks, or an unresolved need for concrete examples. For specific visual borrowing, inspect supplied material or reuse adequate inspected evidence first; research remaining source gaps unless research is explicitly requested. A product or work named only as an atmosphere cue with sufficient direction does not require case research; describe the intended mood without presenting it as verified source behavior or design detail. Begin research with metadata and read usually 1–3 relevant cards, filtering by actual page scope before theme, density or appearance. Do not load the corpus or start both research modules merely because they are available.

The bundled source index includes unreviewed records; a brand name, category or exact-looking token is not proof of official guidance or a working application. Separate official rules, third-party observations/extraction claims, author recommendations and illustrative/synthetic examples. Document review does not verify live behavior. Missing fonts, conflicting values, motion recommendations and unspecified responsive changes remain adaptation work. A marketing example can inform a visual relationship without becoming evidence for business workflow or chart semantics.

Return concrete borrowed traits, case/source identifiers, scope, retained theme and relevant uncertainties to the current decision. Existing product tokens remain authoritative unless a requested change is adopted. If the reference module or source is unavailable, use supplied evidence and existing guidance with the limits stated; no mandatory dependency or invented case is needed. If a project `DESIGN.md` is requested, summarize adopted decisions and link its editable token source rather than adding a competing theme.

## Integrate the decision

Return a short agreement in the target project's existing notes or the requested reply: purpose/region; selected traits (card IDs when useful); why they fit; inherited theme and token source; adopted versus provisional status; intended combinations and local limits; asset needs/fallback; unresolved choice; and which owner integrates the result. Keep it proportional to the task. Do not require a new manifest or write product preferences back into this library.

Global style owns direction advice and shared visual values. Page owners decide layout and business semantics; component owners implement reusable variants; interaction owners handle behavior; responsive owners adapt the agreed structure. A Bento or Split Screen suggestion must yield to the page's real information and action needs. Style choices do not rename statuses, reinterpret chart data, replace interaction contracts, or create another theme source.

Use `ui-ux-pro-max` only for an identified research gap; return its candidates to the same decision, not a second mandatory exploration. A generic “minimalist,” “brutalist,” or “expressive” preference does not invoke an opt-in external skill. The orchestrator retains invocation and regional ownership decisions. `gpt-taste` remains restricted to explicitly selected public marketing work, never business regions. Faithful supplied-image work does not automatically invoke image generation or `image-to-code`.

For implementation, adopt compatible values already produced by the lead or create only missing values in one authoritative product source. For advice, stop at the agreed recommendation. Record only checks actually performed; this reference library alone establishes no rendered UI result.
